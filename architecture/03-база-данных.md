# База данных

> Проектирование БД для прод-версии **tvsalebot** (появится после первого контракта с магазином).
> На MVP БД не используется — контекст диалога живёт в Redis, 12–14 моделей Samsung в [`prompts/models.md`](../prompts/models.md) (правило П1 из [00-правила-проекта.md](00-правила-проекта.md)).
> База опирается на словарь из [02-сущности.md](02-сущности.md) и красные линии из [00-правила-проекта.md](00-правила-проекта.md).

## Что здесь, а что в Redis

**Прод-БД (эта глава):** долговечное хранение — пользователи, согласия, история диалогов, финальные рекомендации, справочник моделей ТВ, аудит удалений, каталог клиента-магазина, лиды для CRM. Хранилище — PostgreSQL в РФ-контуре (Yandex Cloud Managed PostgreSQL или аналог).

**Redis (на MVP и дальше):** короткоживущее состояние активного диалога — лента последних N сообщений для LLM-контекста, собранный профиль покупателя в процессе разговора, текущий шаг воронки. TTL 7 дней на ключ `dialog:<session_id>:*`. При закрытии диалога (`/reset`, финал, таймаут) содержимое Redis **переливается** в соответствующие таблицы БД: `sessions.status='completed'`, `messages`, `buyer_profiles`, `recommendations`. Это гарантирует: быстрый диалог не упирается в SQL, но история не теряется.

**Файлы:** `prompts/system.md`, `prompts/models.md`, `prompts/scenarios.md` остаются файлами и после запуска прод-версии. В БД — только то, что меняет **клиент-магазин** (его каталог, лиды), а не разработчик (промпт, правила воронки).

## Варианты структуры: три подхода и выбор

Задача — не записать первый пришедший в голову вариант. Сравниваю три осмысленных подхода.

### Вариант A — нормализованная реляционная схема

Каждая сущность словаря из [02-сущности.md](02-сущности.md) становится отдельной таблицей со своими полями и FK. Профиль покупателя и рекомендация, хоть и «внутренности диалога», вынесены в отдельные таблицы со связью 1-1 к сессии (так удобнее индексы, миграции и обновления точечных полей, чем менять JSON).

**Плюсы:**
- Прямые индексы по бизнес-полям (бюджет, сценарий) без парсинга JSON — критично для будущих отчётов «сколько клиентов в бюджете до 100к».
- Миграции идут через обычный `ALTER TABLE` — безопасно и постепенно (п. 5).
- Внешний валидатор СУБД ловит битые данные (ненулевой FK, CHECK-ограничения).
- Удаление пользователя одним `DELETE users` с каскадом по FK — закрывает ФЗ-152 одним движением.

**Минусы:**
- Нужно 10 таблиц вместо 3–4. Больше писанины миграций.
- JOIN’ы при подгрузке «всей истории пользователя» — не бесплатные, но на объёмах одного магазина (сотни-тысячи диалогов в день) не узкое место.

### Вариант Б — агрегат «Диалог» в JSONB-колонке

`sessions` — одна таблица, в ней колонка `payload JSONB` держит весь объект диалога целиком (сообщения, профиль, рекомендация). `users`, `tv_models`, `data_deletion_log` остаются отдельно.

**Плюсы:**
- Структура повторяет Redis-ключ один-в-один — простой переход из MVP.
- Запись/чтение одного диалога — один SQL без JOIN’ов.
- Любое изменение формы диалога — без миграции (меняем код сериализации).

**Минусы:**
- Поиск по полям внутри JSONB («все диалоги со сценарием «игры» и бюджетом до 100к») — через GIN-индексы и операторы `@>`, что тормозит и усложняет отчёты.
- Легко потерять инвариант «одна рекомендация на диалог» — внутри JSON такое проверять нельзя через CHECK.
- Теряется строгая связь «рекомендация ссылается на существующую модель ТВ» — внутри JSON можно легко написать несуществующий код модели.
- Прод-версия вводит каталог магазина и лиды — там JSONB уже не поможет, нужны нормальные таблицы. Получится «половина БД реляционная, половина JSONB» — худший из миров.

### Вариант В — event-sourcing (поток событий)

Одна таблица `events` — ровно то, что обсуждалось в [02-сущности.md § Вариант В](02-сущности.md). Любое действие пользователя или бота — строка. Остальные таблицы — проекции.

**Плюсы:**
- Экспорт по ФЗ-152 из коробки — все строки по `telegram_id`.
- Полный аудит каждого шага воронки.
- Готов к мультиканальности (TG → WhatsApp → веб).

**Минусы:**
- Любой простой запрос («какая сейчас текущая рекомендация у этого пользователя») — свёртка по истории или отдельная проекция. Проекция = ещё одна таблица с инвариантами, который нужно поддерживать консистентно.
- Удаление пользователя физически — удалять строки истории, нарушающие сам смысл event-sourcing. Либо хранить псевдо-удалённые события — но это уже не event-sourcing, а помойка.
- Нужно собирать с нуля движок событий. По [правилу П6](00-правила-проекта.md) — такое добавление без явного «ок» запрещено.
- Для нужд одного магазина с десятками диалогов в день — пушкой по воробьям.

### Что выбрал и почему

**Выбрал Вариант A — нормализованная реляционная схема.**

Главный довод: прод-версия (после первого контракта) неизбежно вводит каталог клиента и лиды, где нормальная реляционная модель объективно лучше JSONB. Делать первую половину схемы на JSONB, а потом вторую на обычных таблицах — рецепт противоречий. Лучше сразу один стиль.

Второй довод: ФЗ-152-удаление по `/stop` в Варианте A — один `DELETE users WHERE id = ...` с каскадом по FK. В Вариантах Б и В — либо парсинг JSON, либо чистка событий, что сложнее и опаснее.

Вариант Б остаётся как fallback для ОДНОЙ таблицы — `sessions.funnel_meta` в JSONB для шага воронки и временных флагов, которые не хочется мигрировать по мелочам (см. ниже). Это компромисс: 95% схемы нормальная, одна колонка — свободная форма.

Вариант В — для будущей SaaS-переупаковки с мультиарендатором и аналитикой каждого шага. Пока не нужен.

## Таблицы простым языком

Для каждой таблицы — что хранит, какие поля, зачем каждое поле, кто с кем связан, режим удаления.

**Правила, которые я применяю ко всем таблицам сразу (чтобы не повторять в каждой):**
- У каждой строки — свой `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (или `BIGSERIAL` в терминах PostgreSQL).
- У каждой таблицы — `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` и `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` (updated_at поддерживается триггером, см. раздел «Инварианты»).
- Все деньги — целым числом в копейках (`BIGINT`), никогда `DECIMAL`/`FLOAT`. Нигде не храню `DOUBLE PRECISION` для цен.
- Таймстемпы — с таймзоной (`TIMESTAMPTZ`), всегда UTC.
- Удаление: смотри секцию «Режим удаления» в описании каждой таблицы и общий блок в «Инвариантах».

---

### 1. `users` — Пользователь

**Что хранит:** одного человека в Telegram, который дал согласие на ПДн. Главный агрегат проекта. Пока не дал согласие — записи нет вовсе (это проще, чем держать «пустых» юзеров без согласия).

| Поле | Тип | Зачем |
|---|---|---|
| `id` | BIGINT PK | Внутренний идентификатор для FK в других таблицах. Не `telegram_id`, потому что `telegram_id` формально может быть удалён и переоткрыт тем же человеком — пусть внутренний id будет свой. |
| `telegram_id` | BIGINT NOT NULL UNIQUE | Единственный способ отличить одного пользователя от другого (из [02-сущности.md § 1](02-сущности.md)). Берётся из апдейта Telegram. |
| `entry_point` | TEXT NOT NULL | Через какую точку пришёл: `'start'` (обычный `/start`), `'for_shop'` (`/для_магазина`), `'test'` (тестировщик, помечается вручную). Нужно для B2B-реплики на финале (из [principles.md § 5.2](../idea/principles.md)). |
| `created_at` | TIMESTAMPTZ NOT NULL | Для диагностики и срока хранения. |
| `updated_at` | TIMESTAMPTZ NOT NULL | Поддерживается триггером. |

**Чего нет:** имя, фамилия, телефон, адрес — не спрашиваются, если упомянет в свободной реплике — попадут в `messages.content`, но в отдельные поля не вытаскиваются (принцип минимизации ПДн из [principles.md § 6.2](../idea/principles.md)).

**Режим удаления: физически.** Это ПДн. По `/stop` — `DELETE FROM users WHERE id = ...`, по каскаду умирают consents, sessions, messages, buyer_profiles, recommendations, recommendation_items, leads. В `data_deletion_log` остаётся только `telegram_id + timestamp` (анонимизируется, см. ниже).

**Связи:** 1 → много `sessions`, 1 → 1 `consents`, 1 → много `leads`.

---

### 2. `consents` — Согласие на ПДн

**Что хранит:** одну строку на одного пользователя — текущий статус согласий. Отдельной таблицей (а не колонками в `users`), чтобы на прод-версии добавить второе согласие (маркетинг) без ALTER TABLE в большой таблице.

| Поле | Тип | Зачем |
|---|---|---|
| `user_id` | BIGINT PK, FK → `users(id)` ON DELETE CASCADE | Один consent — один user. Удаление юзера уносит согласие. |
| `pdn_given_at` | TIMESTAMPTZ NOT NULL | Когда человек нажал кнопку согласия на обработку ПДн. Нужно для РКН-выгрузки. |
| `marketing_given_at` | TIMESTAMPTZ NULL | Второе согласие (рассылка). На прод будет кнопка; пока обычно NULL. |
| `policy_version` | TEXT NOT NULL | Версия политики, под которой подписался (например, `'2026-10-25'`). Если политика меняется — пользователь должен подписаться заново. |
| `updated_at` | TIMESTAMPTZ NOT NULL | Через триггер. |

**Чего нет:** истории «давал/отзывал/давал». Если человек отозвал — он удаляется, не остаётся в БД (ФЗ-152 требует удалить). Если потом снова нажмёт `/start` — создаётся заново с новой `created_at`.

**Режим удаления: физически** (каскадом с `users`).

**Связи:** 1 → 1 `users`.

---

### 3. `sessions` — Диалог

**Что хранит:** одну встречу пользователя с ботом. От `/start` или первого сообщения после `/reset` — до финала или таймаута.

| Поле | Тип | Зачем |
|---|---|---|
| `id` | BIGINT PK | Внутренний id. |
| `user_id` | BIGINT NOT NULL, FK → `users(id)` ON DELETE CASCADE | Кому принадлежит. |
| `external_session_id` | TEXT NOT NULL UNIQUE | Тот самый `session_id`, который идёт в `POST /chat` (из [mvp.md § 1.1](../idea/mvp.md)). UUID, видимый из API. |
| `status` | TEXT NOT NULL | `'active'` (сейчас в Redis), `'completed'` (дошли до рекомендации), `'reset'` (пользователь сделал `/reset`), `'abandoned'` (таймаут 7 дней без сообщений). Нужно для фоновой чистки и аналитики. |
| `funnel_step` | TEXT NOT NULL | На каком шаге воронки: `'greeting'`, `'ask_scenario'`, `'ask_light'`, `'ask_distance'`, `'ask_budget'`, `'ask_console'`, `'preparing_recommendation'`, `'recommendation_shown'`, `'safety_shown'`, `'b2b_shown'`. Чтобы бот не задавал один вопрос дважды ([risks.md § 3.3](../idea/risks.md)). |
| `started_at` | TIMESTAMPTZ NOT NULL | Когда начат. |
| `last_message_at` | TIMESTAMPTZ NOT NULL | Для TTL в Redis и фоновой чистки устаревших. |
| `completed_at` | TIMESTAMPTZ NULL | Когда закрыт. NULL пока активен. |
| `created_at` | TIMESTAMPTZ NOT NULL | — |
| `updated_at` | TIMESTAMPTZ NOT NULL | — |

**Чего нет:** колонки `metadata JSONB` — отверг (см. выбор варианта). Все осмысленные поля — явные.

**Режим удаления: физически** (каскадом с `users`). Содержимое диалога — ПДн (пользователь мог написать телефон или адрес в свободной реплике).

**Связи:** много ← 1 `users`, 1 → много `messages`, 1 → 0/1 `buyer_profiles`, 1 → 0/1 `recommendations`.

---

### 4. `messages` — Сообщение

**Что хранит:** одну реплику внутри диалога. На MVP хранились списком в Redis под одним ключом; на прод выделены в таблицу, чтобы можно было считать «сколько раз спрашивали про Dolby Vision» и подобную аналитику ([02-сущности.md § «Чего ещё не знаю»](02-сущности.md) — закрытый вопрос).

| Поле | Тип | Зачем |
|---|---|---|
| `id` | BIGINT PK | Внутренний id. |
| `session_id` | BIGINT NOT NULL, FK → `sessions(id)` ON DELETE CASCADE | К какому диалогу. |
| `role` | TEXT NOT NULL | `'user'`, `'assistant'`, `'system'`. Для правильной подачи в LLM и логов. CHECK IN. |
| `content` | TEXT NOT NULL | Собственно текст реплики. |
| `kind` | TEXT NOT NULL | `'text'` (свободный ввод) или `'button'` (нажатие кнопки). Полезно для аналитики, какие вопросы требовали свободного ответа. |
| `created_at` | TIMESTAMPTZ NOT NULL | Время отправки — для сортировки истории. |

**Чего нет:** `updated_at` — сообщения не редактируются (это лента, append-only); если понадобится, пользователь шлёт новое. Это сокращает триггер и экономит.

**Режим удаления: физически** (каскадом). Текст сообщения — потенциальный ПДн.

**Связи:** много ← 1 `sessions`.

---

### 5. `buyer_profiles` — Профиль покупателя

**Что хранит:** то, что бот успел понять по ходу диалога. Одна строка на один диалог (связь 1 → 0/1). Отдельная таблица, а не колонки в `sessions`, чтобы:
- `UPDATE buyer_profiles SET budget_max = 150000 WHERE session_id = ?` не трогал широкую таблицу `sessions`;
- индексы по полям профиля (бюджет, сценарий) не замедляли записи в `sessions`.

| Поле | Тип | Зачем |
|---|---|---|
| `session_id` | BIGINT PK, FK → `sessions(id)` ON DELETE CASCADE | 1-1 с диалогом. |
| `room_light` | TEXT NULL | `'bright'`, `'dark'`, `'mixed'`, NULL = не спрашивали ещё. Разделитель OLED vs Neo QLED. |
| `distance_m` | DECIMAL(3,1) NULL | Расстояние от дивана до экрана. Переводится в диагональ по формуле × 2,1 см ([references.md Категория 3](../idea/references.md)). |
| `budget_min_kopecks` | BIGINT NULL | Нижняя граница бюджета в копейках. |
| `budget_max_kopecks` | BIGINT NULL | Верхняя граница бюджета в копейках. |
| `console` | TEXT NULL | `'ps5'`, `'xbox_series_x'`, `'pc'`, `'none'`, NULL. Триггер вопроса про HDMI 2.1 и 120 Гц. |
| `preferred_diagonal` | SMALLINT NULL | В дюймах. Если клиент сам назвал. |
| `current_tv_pain` | TEXT NULL | Что не устраивает в текущем ТВ. Свободный текст. Болевые точки = аргументы продажи. |
| `updated_at` | TIMESTAMPTZ NOT NULL | — |

**Про сценарий просмотра:** вынесен в отдельную таблицу `buyer_profile_scenarios` (ниже), потому что сценариев может быть несколько (кино + игры), а переносимый SQL плохо дружит с массивами.

**Чего нет:** колонки «ФИО», «телефон», «адрес», «город» — бот их не спрашивает.

**Режим удаления: физически** (каскадом).

**Связи:** 1 ← 1 `sessions`, 1 → много `buyer_profile_scenarios`.

---

### 6. `buyer_profile_scenarios` — Сценарии просмотра

**Что хранит:** какие сценарии назвал покупатель в этом диалоге. Многие ко многим между диалогом и фиксированным списком сценариев.

| Поле | Тип | Зачем |
|---|---|---|
| `session_id` | BIGINT NOT NULL, FK → `buyer_profiles(session_id)` ON DELETE CASCADE | Чей сценарий. |
| `scenario` | TEXT NOT NULL | `'movies'`, `'sports'`, `'games'`, `'series'`, `'background'`. CHECK IN. |
| PK | (`session_id`, `scenario`) | Один и тот же сценарий не повторяется в одном диалоге. |

**Режим удаления: физически** (каскадом).

---

### 7. `recommendations` — Финальная рекомендация

**Что хранит:** итог диалога — факт, что бот выдал подбор из 2–3 моделей. Одна рекомендация на один диалог ровно (из [02-сущности.md § 2](02-сущности.md): «не больше одной»).

| Поле | Тип | Зачем |
|---|---|---|
| `id` | BIGINT PK | Внутренний id. Нужен для FK из `recommendation_items`. |
| `session_id` | BIGINT NOT NULL UNIQUE, FK → `sessions(id)` ON DELETE CASCADE | 0-1 с диалогом. UNIQUE гарантирует «одна рекомендация». |
| `justification_text` | TEXT NOT NULL | Обоснование, которое LLM сгенерировала и бот показал («подойдёт потому что светлая гостиная + PS5»). Сохраняем ровно тот текст, который видел клиент — для разбора «что бот сказал». |
| `safety_block_shown` | BOOLEAN NOT NULL DEFAULT FALSE | Был ли выдан блок «как безопасно принять ТВ». Чтобы не повторить. |
| `b2b_cta_shown` | BOOLEAN NOT NULL DEFAULT FALSE | Был ли показан переход `/для_магазина`. Чтобы не всплыло второй раз. |
| `created_at` | TIMESTAMPTZ NOT NULL | Когда выдана. |

**Режим удаления: физически** (каскадом).

**Связи:** 0/1 ← 1 `sessions`, 1 → 2–3 `recommendation_items`.

---

### 8. `recommendation_items` — Элементы рекомендации

**Что хранит:** какие конкретно модели ТВ попали в рекомендацию и в каком порядке.

| Поле | Тип | Зачем |
|---|---|---|
| `recommendation_id` | BIGINT NOT NULL, FK → `recommendations(id)` ON DELETE CASCADE | К какой рекомендации. |
| `tv_model_id` | BIGINT NOT NULL, FK → `tv_models(id)` ON DELETE RESTRICT | Ссылка на справочник. RESTRICT — чтобы случайно не удалили модель, которая висит в истории рекомендаций. |
| `rank` | SMALLINT NOT NULL | `1` = базовый, `2` = оптимальный, `3` = топовый. Из [principles.md § 2.1](../idea/principles.md). CHECK BETWEEN 1 AND 3. |
| PK | (`recommendation_id`, `tv_model_id`) | Одна модель — максимум один раз в одной рекомендации. |

**Режим удаления: физически** (каскадом с recommendations). При удалении tv_model — RESTRICT, т.е. нельзя (нужно сначала решить, что делать с историческими рекомендациями).

---

### 9. `tv_models` — Справочник моделей Samsung

**Что хранит:** одну из 12–14 моделей, которые бот «знает». На MVP живёт в `prompts/models.md`; на прод при появлении каталога клиента справочник переносится в БД (чтобы клиент мог сам добавлять свои модели через будущую админку).

| Поле | Тип | Зачем |
|---|---|---|
| `id` | BIGINT PK | — |

| `brightness_nits_min` | SMALLINT NULL | Если известен диапазон. |

| `deleted_at` | TIMESTAMPTZ NULL | Мягкое удаление. См. ниже. |
| `created_at` | TIMESTAMPTZ NOT NULL | — |
| `updated_at` | TIMESTAMPTZ NOT NULL | — |

**Чего нет:** остатки на складе, цена конкретного магазина, фото, ссылки на карточку — у бота нет каталога магазина (из [02-сущности.md § 3](02-сущности.md) и [01-что-строим.md § «Что НЕ войдёт»](01-что-строим.md)).

**Режим удаления: мягкое** (`deleted_at IS NOT NULL`). Это бизнес-факт, не ПДн. Удалённая модель должна оставаться в истории рекомендаций — иначе непонятно, что бот рекомендовал клиенту год назад.

**Связи:** 1 → много `recommendation_items`.

### 10. `data_deletion_log` — Лог удалений по ФЗ-152

**Что хранит:** короткую запись, что по команде `/stop` или `/удалить_данные` данные конкретного пользователя стёрты. Нужна для аудита РКН (из [00-правила-проекта.md § П7в](00-правила-проекта.md)).

| Поле | Тип | Зачем |
|---|---|---|
| `id` | BIGINT PK | — |
| `telegram_id_hash` | TEXT NOT NULL | Хэш (SHA-256) от `telegram_id` + секретной соли, которая живёт в `.env`. Хранится хэш, а не сам ID, чтобы лог сам по себе не был новой базой ПДн. При проверке «удаляли ли мы такого?» — сервис хэширует входящий ID той же солью. |
| `reason` | TEXT NOT NULL | `'user_stop'` (команда `/stop`), `'user_delete'` (`/удалить_данные`), `'retention'` (чистка по сроку). CHECK IN. |
| `deleted_at` | TIMESTAMPTZ NOT NULL DEFAULT NOW() | Момент удаления. |

**Чего нет:** содержимое удалённого диалога, профиль, рекомендация — явный запрет из [00-правила-проекта.md § П7в](00-правила-проекта.md).

**Режим удаления: ничего не удаляется** — это append-only журнал аудита. Чистится только по сроку хранения, который определит юрист заказчика (ориентир — 3 года).

**Связи:** нет FK — пользователя уже нет.

### 11. `catalog_items` — Каталог клиента-магазина (после первого контракта)

**Что хранит:** реальные модели ТВ конкретного магазина с их ценой и наличием. Отдельно от `tv_models` потому что `tv_models` — это знания бота (справочник от разработчика), а `catalog_items` — данные магазина (меняются магазином через интеграцию с его сайтом/1С).

| Поле | Тип | Зачем |
|---|---|---|

| `name` | TEXT NOT NULL | Торговое название в магазине. |
| `category` | TEXT NULL | Категория сайта магазина. |

| `deleted_at` | TIMESTAMPTZ NULL | Мягкое удаление. |
| `created_at` | TIMESTAMPTZ NOT NULL | — |
| `updated_at` | TIMESTAMPTZ NOT NULL | — |

**Режим удаления: мягкое.** Товар может пропасть из каталога (снят с продажи), но лид, который был оформлен на него, — должен ссылаться.

### 12. `leads` — Горячие лиды (после первого контракта)

**Что хранит:** передачу завершённого диалога в CRM магазина (Битрикс24, amoCRM). Создаётся, когда клиент после рекомендации нажал «связаться» или заказал обратный звонок.

| Поле | Тип | Зачем |
|---|---|---|

| `user_id` | BIGINT NOT NULL, FK → `users(id)` ON DELETE CASCADE | Чей лид. Каскад — потому что лид содержит ПДн (телефон, предпочтения). |
| `session_id` | BIGINT NOT NULL, FK → `sessions(id)` ON DELETE CASCADE | Из какого диалога. |
| `status` | TEXT NOT NULL | `'new'`, `'in_crm'`, `'contacted'`, `'won'`, `'lost'`. CHECK IN. |
| `external_crm_id` | TEXT NULL UNIQUE | ID лида в CRM магазина после успешной передачи. UNIQUE: один наш лид = одна проводка в CRM, идемпотентность на случай ретрая передачи. |

| `contact_phone` | TEXT NULL | Если клиент оставил телефон. |
| `created_at` | TIMESTAMPTZ NOT NULL | — |
| `updated_at` | TIMESTAMPTZ NOT NULL | — |

**Режим удаления: физически** (каскадом с users).

## Горячие запросы и индексы

Сначала выписываю, что реально крутится постоянно (не «создать/прочитать запись», а операции, которые повторяются много раз в минуту или идут по расписанию). Под каждый запрос — ровно тот индекс, который его ускоряет. Индексы делаются только под эти запросы, а не наугад.

### Запрос 1 — на каждый `POST /chat`: найти пользователя по Telegram ID

```sql
SELECT u.id, c.pdn_given_at
FROM users u
LEFT JOIN consents c ON c.user_id = u.id
WHERE u.telegram_id = $1;
```

**Индекс:** `UNIQUE INDEX users_telegram_id_uq ON users(telegram_id)` — создаётся автоматически из UNIQUE constraint. Этого достаточно. `consents.user_id` — PK, не нужен отдельный индекс.

### Запрос 2 — на каждый `POST /chat`: подтянуть активный диалог по session_id из API

```sql
SELECT * FROM sessions
WHERE external_session_id = $1 AND status = 'active';
```

**Индекс:** `UNIQUE INDEX sessions_external_session_id_uq ON sessions(external_session_id)` — тоже автоматический из UNIQUE. Фильтр по status внутри уникального ключа дешёвый.

### Запрос 3 — на каждый `POST /chat`: подтянуть последние N сообщений диалога для LLM-контекста

На проде контекст в основном лежит в Redis (быстрый путь), но при промахе кэша и для архивной выдачи — читается из БД.

```sql
SELECT role, content, created_at
FROM messages
WHERE session_id = $1
ORDER BY created_at DESC
LIMIT 20;
```

**Индекс:** `INDEX messages_session_created_idx ON messages(session_id, created_at DESC)`. Композитный — поиск по session_id + сортировка по времени одним проходом.

### Запрос 4 — по команде `/stop`: удалить всё, что принадлежит пользователю

```sql
DELETE FROM users WHERE id = $1;
```

По каскаду умирают consents, sessions (→ messages, buyer_profiles → buyer_profile_scenarios, recommendations → recommendation_items), leads. Каждая каскадная таблица обращается через FK, значит нужны индексы по FK-колонкам, иначе DELETE прочитает её полностью.

**Индексы (создаются автоматически в большинстве СУБД, но проверить):**
- `INDEX sessions_user_id_idx ON sessions(user_id)`
- `INDEX leads_user_id_idx ON leads(user_id)`
- `INDEX messages_session_id_idx` — уже покрыт композитным из Запроса 3.
- `INDEX buyer_profile_scenarios_session_id_idx` — PK (session_id, scenario), префикс покрывает.
- `INDEX recommendation_items_recommendation_id_idx` — PK покрывает.

### Запрос 5 — фоновая чистка «устаревших» активных диалогов (крон раз в час)

Диалог, в котором 7 дней не было сообщений, помечается `abandoned` и его содержимое удаляется из Redis.

```sql
UPDATE sessions
SET status = 'abandoned', completed_at = NOW(), updated_at = NOW()
WHERE status = 'active' AND last_message_at < NOW() - INTERVAL '7 days';
```

**Индекс:** `INDEX sessions_active_last_message_idx ON sessions(last_message_at) WHERE status = 'active'` — partial index, лёгкий, чистый проход только по активным.

### Запрос 6 — для аудита ФЗ-152: все удаления за период

```sql
SELECT * FROM data_deletion_log
WHERE deleted_at BETWEEN $1 AND $2
ORDER BY deleted_at;
```

**Индекс:** `INDEX data_deletion_log_deleted_at_idx ON data_deletion_log(deleted_at)`.

### Запрос 7 — подбор моделей магазина под профиль покупателя (прод, после подключения каталога)

```sql
SELECT ci.*
FROM catalog_items ci
JOIN tv_models tm ON tm.id = ci.tv_model_id
WHERE ci.deleted_at IS NULL
  AND ci.stock_qty > 0
  AND tm.tv_class = $1
  AND ci.price_kopecks BETWEEN $2 AND $3;
```

**Индекс:**
- `INDEX catalog_items_class_price_idx ON catalog_items(tv_model_id, price_kopecks) WHERE deleted_at IS NULL AND stock_qty > 0` — partial index, покрывает горячий путь подбора.
- `INDEX tv_models_class_idx ON tv_models(tv_class) WHERE deleted_at IS NULL` — для фильтра по классу.

## Инварианты (правила, которые база никогда не должна нарушать)

**И1. У каждой записи есть свой уникальный `id` (BIGINT PK).**

**И2. У каждой таблицы есть `created_at` и `updated_at` (кроме `messages`, `recommendation_items`, `buyer_profile_scenarios`, `data_deletion_log` — там только `created_at` или `deleted_at`, т.к. строки не редактируются).**

Поддерживается триггером:

```sql
CREATE OR REPLACE FUNCTION touch_updated_at() RETURNS TRIGGER AS $$
BEGIN NEW.updated_at = NOW(); RETURN NEW; END;
$$ LANGUAGE plpgsql;

-- и для каждой таблицы:
CREATE TRIGGER <table>_touch_updated_at
  BEFORE UPDATE ON <table>
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
```

**И3. Нет ссылок на несуществующее.** Все связи между таблицами — через FOREIGN KEY. Поведение `ON DELETE`:

| Направление | Поведение | Почему |
|---|---|---|
| `users` → `consents`, `sessions`, `leads` | CASCADE | Удаление юзера уносит его ПДн. |
| `sessions` → `messages`, `buyer_profiles`, `recommendations`, `leads` | CASCADE | Содержимое диалога — ПДн. |
| `buyer_profiles` → `buyer_profile_scenarios` | CASCADE | Часть профиля. |
| `recommendations` → `recommendation_items` | CASCADE | Часть рекомендации. |
| `tv_models` → `recommendation_items` | RESTRICT | Нельзя удалить модель, пока она висит в истории рекомендаций. |
| `tv_models` → `catalog_items` | SET NULL | Товар магазина может пережить удаление справочной модели. |

**И4. Удалённое не возвращается в обычных запросах.** Для таблиц с мягким удалением (`tv_models`, `catalog_items`) — все запросы приложения добавляют `WHERE deleted_at IS NULL`. Чтобы это не зависело от памяти разработчика, создаются VIEW:

```sql
CREATE VIEW tv_models_v AS SELECT * FROM tv_models WHERE deleted_at IS NULL;
CREATE VIEW catalog_items_v AS SELECT * FROM catalog_items WHERE deleted_at IS NULL;
```

Приложение читает через `*_v`, пишет напрямую. Прямой `SELECT * FROM tv_models` используется только в скриптах аудита.

**И5. Режим удаления выбран осознанно по типу данных:**

| Таблица | Режим | Почему |
|---|---|---|
| `users` | физически | ПДн (telegram_id — идентификатор человека). |
| `consents` | физически | ПДн (отражает согласие конкретного человека). |
| `sessions` | физически | Содержит ПДн через сообщения. |
| `messages` | физически | Текст может содержать ФИО/телефон. |
| `buyer_profiles` | физически | Бюджет, бытовые привычки — ПДн. |
| `buyer_profile_scenarios` | физически | Часть профиля. |
| `recommendations` | физически | Привязано к ПДн-диалогу. |
| `recommendation_items` | физически | Часть рекомендации. |
| `leads` | физически | Содержит контакт покупателя. |
| `tv_models` | мягко | Справочник. Бизнес-факт. История рекомендаций должна жить. |
| `catalog_items` | мягко | Бизнес-факт магазина, нужен в истории лидов. |
| `data_deletion_log` | не удаляется | Append-only, журнал аудита по сроку хранения юриста. |

**Правила «мягко везде по умолчанию» нет** — для ПДн всегда физическое удаление.

**И6. Уникальность, которая несёт смысл:**
- `users.telegram_id UNIQUE` — один человек = одна запись.
- `sessions.external_session_id UNIQUE` — API-идентификатор уникален глобально.
- `recommendations.session_id UNIQUE` — максимум одна рекомендация на диалог.
- `tv_models.code UNIQUE` — код модели уникален.
- `catalog_items.sku UNIQUE` — артикул магазина уникален.
- `leads.external_crm_id UNIQUE` — повторный приход callback’а от CRM не создаст дубликат.

**И7. CHECK-ограничения (валидация внутри БД, не только в коде):**

```sql
ALTER TABLE users ADD CONSTRAINT users_entry_point_chk
  CHECK (entry_point IN ('start', 'for_shop', 'test'));

ALTER TABLE sessions ADD CONSTRAINT sessions_status_chk
  CHECK (status IN ('active', 'completed', 'reset', 'abandoned'));

ALTER TABLE messages ADD CONSTRAINT messages_role_chk
  CHECK (role IN ('user', 'assistant', 'system'));

ALTER TABLE messages ADD CONSTRAINT messages_kind_chk
  CHECK (kind IN ('text', 'button'));

ALTER TABLE buyer_profiles ADD CONSTRAINT buyer_profiles_budget_chk
  CHECK (budget_min_kopecks IS NULL
      OR budget_max_kopecks IS NULL
      OR budget_min_kopecks <= budget_max_kopecks);

ALTER TABLE tv_models ADD CONSTRAINT tv_models_price_chk
  CHECK (price_min_kopecks <= price_max_kopecks);

ALTER TABLE recommendation_items ADD CONSTRAINT rec_items_rank_chk
  CHECK (rank BETWEEN 1 AND 3);

ALTER TABLE leads ADD CONSTRAINT leads_status_chk
  CHECK (status IN ('new', 'in_crm', 'contacted', 'won', 'lost'));
```

**И8. Деньги — только целым числом в копейках (BIGINT).** Нигде нет `DECIMAL(x,2)` для денег и уж тем более `FLOAT`. Все колонки с деньгами называются `*_kopecks` чтобы было видно сразу. Самого приёма платежей в tvsalebot нет (из [00-правила-проекта.md](00-правила-проекта.md): «Денежных операций в самом боте нет»), но тот же принцип применён к ценам справочника и каталога.

**И9. «Один внешний идентификатор = одна проводка».** Для `leads.external_crm_id` действует `UNIQUE`. Передача лида в CRM — через INSERT с `ON CONFLICT (external_crm_id) DO NOTHING` (или через SELECT-перед-INSERT в транзакции). Если callback от CRM придёт дважды — второй INSERT просто ничего не сделает. Это защита от двойной обработки, перенесённая из правил работы с платежами в правила работы с внешними ID вообще.

**И10. Все таймстемпы — в UTC с таймзоной (`TIMESTAMPTZ`).** На уровне приложения показываем в Europe/Moscow, но в БД храним с таймзоной.

## Как менять базу позже без потери данных

**М1. Инструмент миграций — Alembic** (под будущий Python-стек прод-версии). Решение зафиксировать в [05-стек.md](05-стек.md) при его финализации.

**М2. Каждое изменение — отдельный файл миграции со своей датой/версией.** Файл кладётся в `migrations/versions/`, именуется `YYYYMMDDHHMM_<slug>.py`. В миграции — ровно одно смысловое изменение (новая таблица, новая колонка, новый индекс, переименование).

**М3. Уже применённое изменение никогда не переписываем.** Если миграция № 20270115_add_phone ушла на прод и применилась — её файл не правим. Ошибка исправляется новой миграцией № 20270116_fix_phone.

**М4. Удаление поля с живыми данными — всегда в два захода:**

Шаг 1 (релиз N): перестаём читать и писать в поле на уровне приложения — колонка остаётся в БД, но код её игнорирует.

Шаг 2 (релиз N+1, через 1–2 недели эксплуатации): отдельная миграция `ALTER TABLE ... DROP COLUMN ...`.

Это защищает от сценария «старый инстанс сервиса ещё поднят, уже без колонки, падает на SELECT».

**М5. Миграции применяются только вперёд (upgrade).** Rollback (downgrade) — есть в Alembic по умолчанию, но на проде используем только для **свежеразвёрнутой** миграции, которую сами только что применили и сразу поняли, что сломали. Для миграций старше суток — откат только через новую миграцию «обратного действия».

**М6. Не оптимизируем под объёмы, которых пока нет.** Нет партицирования `messages` по дате, нет шардирования `users` по telegram_id, нет read-replica. Эти штуки появляются, когда реальный профиль нагрузки показал, что без них не выжить. На объёмах одного магазина (сотни-тысячи диалогов в день) обычная PostgreSQL-инстанция справляется без ухищрений.

**М7. Каждая миграция, меняющая схему, — одна строка в [architecture/decisions.md](decisions.md)** (из правила П5): `YYYY-MM-DD — миграция <slug> — зачем`. Чтобы через год не ломать голову, зачем мы добавляли колонку `old_metadata JSONB`.

BEGIN
  NEW.updated_at = NOW();

END;
$$ LANGUAGE plpgsql;

## Решения, которые я сделал сам (пометки для возврата)

Из открытых вопросов в [02-сущности.md § «Чего ещё не знаю»](02-сущности.md) закрыл:

- **Сколько диалогов на пользователя — несколько.** После `/reset` старый диалог помечается `status='reset'`, но физически остаётся — на прод-версии нужна аналитика «сколько повторных визитов, какова конверсия по сценариям». При `/stop` всё равно удаляется каскадом.
- **Отдельный «тип пользователя» — не нужен.** Хватает поля `users.entry_point` с тремя значениями: `start` / `for_shop` / `test`.
- **Сообщения отдельной таблицей на прод — да.** Отчёты «сколько раз спрашивали про Dolby Vision» и анализ конверсии требуют реляционного доступа; хранить сообщения в JSONB было бы шагом назад.

Если какое-то из этих решений не подходит — поправлю в один проход, пока не ушли миграции в прод.

## Журнал решений

- **Решение: выбрал нормализованную реляционную схему (вариант А) с мягким удалением только для справочников и каталога, физическим — для всех ПДн, потому что это даёт одновременно самый простой ФЗ-152-удалятор по `/stop` (один `DELETE users` с каскадом), прямые индексы под реальные горячие запросы (JOIN’ы, фильтры по бюджету и классу), валидацию инвариантов самой СУБД (FK + CHECK + UNIQUE) и один стиль схемы для первой и второй половины прод-версии (пользовательские диалоги + каталог/лиды), а не половинчатый JSONB-гибрид (вариант Б) и не event-sourcing (вариант В), который на объёмах одного магазина — пушкой по воробьям и прямо запрещён правилом П6 без явного согласования.**
