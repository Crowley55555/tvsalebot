# Стек

> Выбор технологий для **tvsalebot** (AI-продажник Samsung TV в Telegram).
> Опирается на идею из [idea/](../idea/) и ранее принятые решения в [01-что-строим.md](01-что-строим.md), [02-сущности.md](02-сущности.md), [03-база-данных.md](03-база-данных.md), [04-потоки-данных.md](04-потоки-данных.md), [00-правила-проекта.md](00-правила-проекта.md).

## Входные данные для выбора

**Персональные данные граждан РФ — ДА.** Продукт собирает: `telegram_id` пользователя, факт согласия на обработку ПДн, собранный профиль покупателя (бюджет, расстояние до экрана, консоль, сценарий просмотра), ленту сообщений (в которой пользователь может сам написать ФИО/телефон/адрес). Из этого следуют две жёсткие рамки:

- **база ПДн — только в РФ** (152-ФЗ, ст. 18 ч. 5: «базы данных граждан РФ размещаются на территории РФ»);
- **LLM в продакшене — только РФ-провайдер** (152-ФЗ, ст. 12 — трансграничная передача без основания запрещена; штраф по ст. 13.11 КоАП — от 150 тыс. до нескольких млн ₽, см. [deep-research.md § 5.5](../idea/deep-research.md)).

**Серверы под продукт уже выделены:**
- **NL-сервер (Нидерланды)** — для aiogram-бота (Telegram-транспорт, stateless-прокси; никаких ПДн на диске/в кэше дольше одного запроса);
- **РФ-сервер (Россия)** — для Core API, Redis, PostgreSQL (прод) — вся база ПДн здесь.

**Схема «NL = транспорт, РФ = ядро» формально задействует трансграничную передачу** (ст. 12 ФЗ-152): каждое пользовательское сообщение проходит через NL-сервер транзитом в РФ-ядро. Нидерланды — страна с адекватным уровнем защиты по приказу РКН, поэтому передача допустима **при подаче уведомления в РКН** (бесплатно, срок — до начала фактической обработки). На MVP (демо для одного клиента, без реальных покупателей) риск принимается осознанно; подача уведомления — в бэклог «перед первой выдачей ссылки реальным покупателям магазина» ([mvp.md § 7](../idea/mvp.md)).

**Файлов продукт не создаёт и не принимает** ([03-база-данных.md § «Файлы»](03-база-данных.md), [04-потоки-данных.md § 4.7](04-потоки-данных.md)). Весь обмен — текст и кнопки в Telegram.

**Денежных операций в самом боте нет** ([00-правила-проекта.md § «Что сломать нельзя»](00-правила-проекта.md)). Расчёт с клиентом-магазином за разработку происходит вне бота.

## Бюджет жетонов

У стартапа три жетона на экзотические/новые/редкие технологии. **Один жетон уже забронирован на LLM** (это не веб-фреймворк, не БД, не хостинг — на этом рынке нет «скучного проверенного» выбора «из коробки», каждый провайдер — отдельная история).

Оставшиеся два жетона держу в кармане:
- один — как резерв на непредвиденное на проде (например, когда появится веб-виджет или голосовой канал);
- второй — на одну прод-опцию из этого же файла (arq-очередь), которая вступит в игру только после первого контракта.

**Всё остальное — максимально скучное и проверенное.** Там, где есть выбор между «новым модным» и «работает у тысяч проектов 10+ лет» — беру второе.

## Выбор по частям продукта

Для каждой части: сравнение минимум двух вариантов → что выбрал → запасная альтернатива → одна строка «почему именно это под мою идею».

### 1. Язык

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Python 3.11+** | Один язык и для LLM-клиентов (GigaChat/YandexGPT SDK — Python-first), и для веба (FastAPI), и для бота (aiogram); я на нём пишу каждый день; типизация через Pydantic. | Чуть медленнее на CPU-задач; в проекте CPU-задач нет вообще — всё I/O. |
| Node.js / TypeScript | Отличный async, тоже один язык для фронта и бэка. | SDK GigaChat/YandexGPT менее зрелые на TS; придётся переучиваться — а это жетон. |
| Go | Быстрее, компилируется в бинарник. | Чужой стек для меня (переобучение = жетон); для 1 эндпоинта и бота — пушкой по воробьям. |

**Выбрал:** Python 3.11+.
**Запасная альтернатива:** Node.js / TypeScript.
**Почему под мою идею:** я джуниор-мидл на Python, и у GigaChat/YandexGPT именно Python-SDK работают из коробки — экзотики ноль, жетон не тратится.

### 2. Веб-часть (Core API)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **FastAPI + Pydantic v2 + Uvicorn** | Де-факто стандарт для LLM-бэкендов на Python; async-first; схемы запросов/ответов валидируются Pydantic'ом автоматически (правило П3). | Чуть моложе Flask (но зрелый с 2018 года, тысячи прод-проектов). |
| Flask + Marshmallow | Самый старый и зрелый микро-фреймворк Python. | Исторически sync; async-поддержка есть, но клеится; валидация внешней либой. |
| Django REST Framework | Батарейки включены (админка, ORM, миграции). | Для одного эндпоинта `POST /chat` — слон в посудной лавке; async только частично. |

**Выбрал:** FastAPI + Pydantic v2 + Uvicorn (ASGI-сервер).
**Запасная альтернатива:** Flask + Marshmallow.
**Почему под мою идею:** 90% времени Core API ждёт ответ от GigaChat, поэтому async обязателен; Pydantic закрывает инвариант П3 из правил проекта (валидация на границе `POST /chat`) без лишнего кода.

### 3. Telegram-бот (транспорт)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **aiogram 3.x** | Async-first, зрелая FSM, активная экосистема, хорошая документация на русском, уже заложено в [mvp.md § 3](../idea/mvp.md). | Третья мажорная версия — API менялось; это принято. |
| python-telegram-bot 20.x | Самый старый питоновский бот-фреймворк. | До 20-й версии был sync; на async переехал поздно и шероховато. |
| pyTelegramBotAPI (telebot) | Самый простой. | Слабая FSM, слабый async. |

**Выбрал:** aiogram 3.x.
**Запасная альтернатива:** python-telegram-bot 20.x.
**Почему под мою идею:** async того же стиля, что FastAPI (один event-loop, один `httpx.AsyncClient`); FSM-роутинг покрывает воронку диалога без ручного state-machine (см. [04-потоки-данных.md § 5](04-потоки-данных.md)).

### 4. База данных

| Вариант | Плюсы | Минусы |
|---|---|---|
| **PostgreSQL 15+ (на MVP не используется, на прод — Managed в Yandex Cloud / VK Cloud / Selectel)** | Самая зрелая реляционная БД; строгие FK + CHECK + UNIQUE закрывают инварианты из [03-база-данных.md § «Инварианты»](03-база-данных.md); каскадное удаление по `/stop` — одной строкой; есть partial indexes и JSONB для редких случаев; все три крупных облачных провайдера РФ дают Managed PostgreSQL с резервным копированием и репликацией. | На MVP не нужна вообще (контекст в Redis). |
| MySQL 8+ | Тоже зрелый. | Хуже с partial indexes и типом JSONB; меньше ловушек, но и меньше возможностей для редких случаев, которые нам всё же пригодятся на проде (аудит, аналитика). |
| MongoDB | Удобен для JSON-подобных документов. | Нам нужны FK (каскадное удаление ПДн), CHECK (валидация ролей, статусов), UNIQUE (идемпотентность `external_crm_id`) — всё это слабо/никак в документной БД; на объёмах одного магазина — не выигрывает ни в чём. |

**Выбрал:** PostgreSQL 15+ (Managed в РФ-облаке). На MVP БД не поднимается — контекст живёт в Redis (решение зафиксировано в [03-база-данных.md](03-база-данных.md)).
**Запасная альтернатива:** MySQL 8+.
**Почему под мою идею:** вся схема из [03-база-данных.md](03-база-данных.md) опирается на FK ON DELETE CASCADE (это ФЗ-152-удалятор одним движением), partial indexes (горячие запросы на фильтре активных сессий) и CHECK (роли сообщений, статусы лидов) — на MySQL часть этого делается хуже или сложнее.

### 5. Горячее состояние диалога (кэш и контекст)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Redis 7 (на MVP — один инстанс рядом, на прод — Managed Redis в РФ)** | Атомарные SETNX (локи от двойного клика, § 4.3), TTL из коробки, списки для истории сообщений, hash для профиля; знаком, в экосистеме Python async-клиент `redis-py` зрелый. | Экзотики нет. |
| Memcached | Проще. | Нет TTL с миллисекундной гранулярностью, нет SETNX, нет персистентности — для нашего кейса слабее по всем пунктам. |
| PostgreSQL без Redis | Один слой хранения. | На горячем пути `POST /chat` каждое чтение/запись лишний round-trip к БД — лишние 2–5 мс × 4 операции на одно сообщение. |

**Выбрал:** Redis 7.
**Запасная альтернатива:** Managed Memcached в том же облаке.
**Почему под мою идею:** на MVP вся «БД» — это Redis; и после подключения PostgreSQL на проде Redis остаётся как горячий кэш активных сессий + лок от двойного клика (§ 4.3) + журнал `pending_user_message` (§ 3.5) — ничего из этого PostgreSQL делать быстро не умеет.

### 6. Хостинг (где всё работает)

**Серверы уже выделены (вопрос «у кого купить» не стоит).** Решается только одно: **что крутится где**. Выбор зафиксирован — **схема B** из развилки по развёртыванию, после ревизии рисков в [09-риски.md § С4](09-риски.md): aiogram и Core API живут на РФ-сервере, NL-сервер используется только как **SOCKS5/WireGuard-прокси для исходящих HTTPS-запросов к `api.telegram.org`**. Главный выигрыш — ПДн граждан РФ физически не покидают РФ-контур ни на одном шаге, значит трансграничная передача по ст. 12 ФЗ-152 **не задействована**, уведомление в РКН до старта MVP не требуется.

| Что | Где | Почему именно сюда |
|---|---|---|
| **aiogram-бот** (транспорт Telegram, FSM, парсинг Telegram Update, отправка ответов пользователю) | **РФ-сервер** | aiogram ведёт long-poll `getUpdates` через SOCKS5-туннель на NL; все апдейты (включая содержимое сообщений граждан РФ) обрабатываются **только** в РФ, LLM-вызов идёт из РФ, Redis — в РФ. |
| **Core API (FastAPI)** | **РФ-сервер** | Валидирует Pydantic, вызывает LLM, пишет в Redis — всё это **обработка ПДн**, по 18 ч. 5 ФЗ-152 должна жить в РФ. |
| **Redis** (контекст активных сессий, профиль, история) | **РФ-сервер** | База ПДн граждан РФ — только РФ-контур. |
| **PostgreSQL** (прод, после первого контракта) | **РФ-сервер** → Managed PostgreSQL в Yandex Cloud / VK Cloud (когда перерастём один VPS) | Та же причина. |
| **LLM (GigaChat 2 Pro)** | облако Сбера, РФ-контур | Трафик `GigaChatClient` в облако Сбера идёт **из РФ-сервера**. ПДн из Redis → GigaChat → ответ, всё внутри РФ. |
| **SOCKS5/WireGuard-прокси для исходящих запросов к Telegram API** | **NL-сервер (Нидерланды)** | Выполняет **только** транспортную функцию: пробрасывает TLS-туннель от РФ-сервера к `api.telegram.org`. TLS устанавливается из aiogram-клиента в РФ напрямую к Telegram; NL видит только `CONNECT api.telegram.org:443`, не содержимое сообщений. |

**Как связаны РФ и NL:**
- aiogram на РФ-сервере поднимает SOCKS5-соединение с NL на выделенном порту (авторизация по SSH-ключу или user/password из `.env`), подключается через `aiohttp_socks` — одна строка в `bot/main.py`.
- Все HTTP-запросы к Telegram Bot API (`https://api.telegram.org`) идут через этот туннель. SOCKS5 не терминирует TLS, значит NL никогда не видит открытый HTTP-трафик — только зашифрованный TLS-поток, установленный клиентом из РФ.
- Core API больше **не слушает публичный HTTPS**: aiogram и Core API живут на одной машине и разговаривают по локальному сокету `http://127.0.0.1:8000/chat`. nginx с Let's Encrypt — **не нужен** на MVP, снимаются сопутствующие операционные риски (просрочка сертификата, настройка firewall для внешних IP).
- Публичным остаётся только `GET /health` на отдельном порту для UptimeRobot — без ПДн, статический JSON.
- Полная задержка на одно сообщение: TG → NL (~30 мс, TLS-туннель) + NL → РФ (~30 мс) + aiogram + Core API + LLM (2–8 с) + ответ обратно. Доп. 60 мс к обычному циклу — незаметно для пользователя.

**NL-сервер — только транспортный прокси** (принято как инвариант):
- На NL **не разворачивается** код проекта (ни `bot/`, ни `api/`, ни `prompts/`): только SOCKS5-сервер (`dante-server` или `3proxy`).
- Логи SOCKS5-сервера содержат **только** строки вида `CONNECT api.telegram.org:443`, без содержимого сообщений, без `telegram_id`. NL-сервер не является местом хранения ПДн ни по одному признаку.
- Доступ к NL — только по SSH-ключу разработчика + белый список IP РФ-сервера на SOCKS5-порту.

**Запасная альтернатива** (схема A — прежний вариант, оставлена как fallback на случай блокировки SOCKS5-трафика к Telegram API со стороны NL-провайдера): aiogram возвращается на NL-сервер, Core API остаётся в РФ, связь между ними — HTTPS с bearer-токеном и IP-whitelist. В этом случае ПДн транзитом проходят через NL — требуется подача уведомления РКН о трансграничной передаче перед выдачей ссылки кому-либо (включая клиента-магазина). Переключение между схемой B и схемой A — одна переменная окружения `TELEGRAM_PROXY_MODE=socks5|direct`; разделение `bot/` и `api/` по правилу П3 позволяет и ту, и другую топологию без правок в ядре.

**Почему именно эта раскладка под мою идею:**
- ПДн граждан РФ физически не покидают РФ-контур — трансграничная передача по ст. 12 ФЗ-152 не задействована, бумажная процедура с РКН не блокирует старт MVP (см. [09-риски.md § С4](09-риски.md), главный смертельный риск проекта).
- Полностью используются оба уже имеющихся сервера (NL + РФ) — нулевые затраты на VPS сверх текущих.
- Разделение труда по границе `bot/` vs `api/` из [00-правила-проекта.md § П3](00-правила-проекта.md) сохраняется, но физически обе папки едут на один РФ-сервер; это сокращает одну публичную поверхность атаки (nginx HTTPS между NL и РФ — больше нет).
- Один взлом NL ≠ потеря ПДн: даже root на NL видит только SOCKS5-логи `CONNECT api.telegram.org:443` без содержимого; получив root на РФ, атакующий видит ПДн, но для их отправки наружу нужно пройти через NL-прокси, который может быть внезапно отключён разработчиком одной командой.

### 7. Объектное хранилище для файлов

**Файлов в продукте нет.** Продукт не создаёт и не принимает ни фото ТВ, ни видео, ни PDF-отчётов (из [03-база-данных.md § «Файлы»](03-база-данных.md), [04-потоки-данных.md § 4.7](04-потоки-данных.md)). Соответственно, объектное хранилище на MVP и в первой прод-версии **не нужно**.

**Если появится потом** (например, в прод-версии бот начнёт отдавать PDF-КП или импортировать каталог из Excel): **Yandex Object Storage** (S3-совместимое, серверы в РФ), запасная альтернатива — **VK Cloud Storage**. В БД — только метаданные + подписанная ссылка с коротким TTL. Эти слова — задел на будущее, в MVP не включается.

### 8. Фоновые и отложенные задачи (очередь, расписание)

| Вариант | Плюсы | Минусы | Когда |
|---|---|---|---|
| **MVP — без очереди, прямо в async-хэндлере** (`await llm.chat(...)`) | Нулевой код сверх FastAPI + aiogram; ответ пользователю без промежуточного ack; нет лишнего процесса в деплое. | Падение процесса в середине LLM-вызова = потеря ответа; на MVP это редкий кейс, покрывается ретраями из `GigaChatClient`. | **MVP.** |
| **Прод — arq (async-очередь на Redis)** | asyncio-first (не ломает стиль FastAPI+aiogram); из коробки — ретраи, deadletter, таймауты; работает на том же Redis-инстансе, что контекст, — ни одного нового сервиса. | +1 библиотека и +1 процесс (воркер); беру жетон (это не Celery/RQ — arq моложе и реже встречается). | **Прод** (после подключения CRM и каталога, когда появятся платные идемпотентные операции с ретраями на часы). |
| Celery + Redis | Самая взрослая очередь в Python-мире. | sync-first, с asyncio-клиентами FastAPI/aiogram клеится через боль. |
| cron (systemd timer) для расписания | Самый скучный планировщик. | Для MVP нужен только один тикет-крон (чистка 7-дневных сессий, см. § С12), это закрывается `systemd`-таймером без очереди. |

**Выбрал:**
- **MVP:** без очереди (прямо в async-хэндлере) + `systemd timer` для фоновой чистки устаревших сессий.
- **Прод:** arq (с жетоном №2) поверх того же Redis.

**Запасная альтернатива:** Celery (с принудительным sync-враппингом вокруг async-клиентов LLM/CRM).
**Почему под мою идею:** в MVP одна «тяжёлая» задача — вызов LLM, он помещается в `POST /chat` под синхронным ожиданием; на проде появятся CRM-webhook'и и ретраи-на-часы, которые без очереди не живут, и arq — самый асинхронный способ не выйти за Redis-инфраструктуру.

### 9. ИИ-модель (жетон №1)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **GigaChat 2 Pro (Freemium) — MVP; GigaChat Pro pay-as-you-go — прод** | Серверы в РФ → ФЗ-152 из коробки; **40 млн токенов/год бесплатно** на период MVP (это критично для экономики проекта: $0 LLM-расходов до первого контракта); официальный Python-SDK. | Качество рассуждений ниже топовых мировых; хватает ли — проверяется в [proof-of-value.md § 2](../idea/proof-of-value.md) на пяти эталонных сценариях. |
| YandexGPT 5 Pro | Тоже в РФ; аналогичный уровень качества; хороший альтернативный поставщик для fallback. | Платный с первых токенов (нет аналога Freemium 40 млн/год); ниже приоритет для MVP. |
| ❌ OpenAI GPT-4 / Anthropic Claude / Google Gemini | Лучшее качество рассуждений. | **Запрещено по ФЗ-152 в продакшене** (трансграничная передача ПДн граждан РФ без основания). Допустимо только в dev-режиме на анонимных данных ([00-правила-проекта.md § П7б](00-правила-проекта.md)). |
| ❌ Своя LLM на Ollama (Llama/Mistral в контуре) | Полный контроль, никаких трансграниц. | Для нормального качества нужны видеокарты от 24 ГБ; хостинг таких — от 50 000 ₽/мес, съедает всю экономику MVP; качество открытых моделей на русском — ниже GigaChat. |

**Выбрал:** GigaChat 2 Pro через Freemium (на период MVP) → pay-as-you-go после первого контракта.
**Запасная альтернатива:** YandexGPT 5 Pro (fallback, подключается через тот же порт `LLMClient` одним файлом-адаптером).
**Почему под мою идею:** закрывает одновременно два требования — ФЗ-152 (серверы в РФ) и 0 ₽/мес на время MVP (40 млн токенов на год); это единственный ИИ-провайдер в мире, который даёт одновременно оба условия, — поэтому именно сюда уходит жетон №1.

### 10. Оплата

**В самом боте оплаты нет.** Пользователь ничего не покупает через бота — бот только консультирует и переводит на `/для_магазина`. Платежей от пользователя-покупателя продукту мы не принимаем ([00-правила-проекта.md § «Денежных операций в самом боте нет»](00-правила-проекта.md)).

Расчёт с клиентом-магазином за разработку бота — отдельный процесс, вне продукта (счёт от ИП/самозанятого, предоплата 50% по [mvp.md § 6](../idea/mvp.md)). В стек продукта это не входит.

**Если в прод-версии появится приём платежей** (например, подписочная SaaS-переупаковка из [vision.md](../idea/vision.md), «коробочный продукт»): **ЮKassa** (ЮMoney/Сбер) — самый скучный и проверенный РФ-эквайринг; запасная альтернатива — **Robokassa** / **Тинькофф Касса**. Обе — РФ-резиденты, с 54-ФЗ-чеками из коробки. Это задел на будущее, в MVP и первой прод-версии не включается.

## 3 числа, которые смотрю каждый день

Критерии: число понятно за секунду, падение числа говорит о реальной проблеме, измерение не требует отдельного BI-инструмента.

| Число | Что показывает | Чем мерить (MVP) | Чем мерить (прод) |
|---|---|---|---|
| **1. Процент диалогов, дошедших до рекомендации (конверсия воронки)** | Главный бизнес-индикатор демо: если из 10 посетителей 0 доходит до финала — бот плохо продаёт, вся идея не работает. | Счётчик `funnel:started` и `funnel:recommended` в Redis, обнуляемый ежедневно. Строчка в журнале разработчика раз в день. | SQL-отчёт: `COUNT(DISTINCT session_id) WHERE funnel_step='recommendation_shown'` / `COUNT(DISTINCT session_id)` за сутки. |
| **2. SLA вызовов LLM за день (успех против карантина)** | Проверка здоровья главной внешней зависимости: деградация GigaChat → молча плохие ответы → утеря доверия клиента. | Счётчики `llm:ok:<YYYY-MM-DD>` и `llm:fail:<YYYY-MM-DD>` в Redis. Простая строка «OK: 94, FAIL: 2 → 97.9%». | Тот же счётчик + алерт из UptimeRobot / Grafana при SLA < 97%. |
| **3. Расход токенов LLM за день (vs. дневной потолок)** | Защита от бага «бот ушёл в бесконечный цикл длинных ответов и за день съел квоту», плюс прогноз, доживёт ли Freemium до первого контракта. | Ключ `llm:budget:<YYYY-MM-DD>:tokens_used` в Redis, уже заложен в [04-потоки-данных.md § 5.4](04-потоки-данных.md). | То же + ежедневная агрегация в `daily_metrics` на проде. |

**Эти три числа — не аналитика, а приборная панель.** Их видно без BI, они не требуют отдельного процесса, они закрывают три разных вида проблем (продукт, инфраструктура, экономика).

## Порты и адаптеры (внешние зависимости)

Любая внешняя услуга, которая может: подорожать, лечь, сменить API, попасть под санкции — живёт за **портом** (абстрактный интерфейс «что нам нужно») в `core/`, и к нему подключается **адаптер** (конкретная реализация под конкретного вендора) в том же `core/`.

**Правило:** ядро (`api/`, бизнес-логика в `core/`) зовёт только порт. О вендоре знает только файл-адаптер. **Смена вендора = новый файл-адаптер + одна строка в конфиге + ноль правок в ядре.** Это уже заложено в [00-правила-проекта.md § П2](00-правила-проекта.md).

Ниже — полный список портов, в которые завёрнуты внешние зависимости продукта.

### Порт 1: `LLMClient` — генерация ответа консультанта

**Что ядро хочет:** «сгенерируй ответ для вот этого списка сообщений с этим системным промптом; верни текст или ошибку».

```python
# core/llm.py
class LLMClient(Protocol):
    async def chat(
        self,
        system_prompt: str,
        messages: list[Message],
        *,
        max_tokens: int,
        timeout_s: float,
    ) -> ChatResult: ...
```

**Адаптеры:**
- `core/llm_gigachat.py` → `GigaChatClient` (**по умолчанию, прод-safe**).
- `core/llm_yandex.py` → `YandexGPTClient` (fallback, прод-safe).
- `core/llm_openrouter.py` → `OpenRouterClient` (**только dev**, только анонимные данные; защита — проверка `ENVIRONMENT=prod` и `LLM_PROVIDER in ("gigachat", "yandex")` в [settings.py](../api/settings.py)).

**Смена провайдера на проде:** `LLM_PROVIDER=yandex` в `.env` — и всё, ядро не трогаем.

### Порт 2: `MessageTransport` — приём и отправка сообщений в канале

**Что ядро хочет:** «получи от пользователя сообщение, передай его в Core API, доставь ответ пользователю».

```python
# core/transport.py
class MessageTransport(Protocol):
    async def send(self, user_id: str, text: str, kind: str = "text") -> None: ...
    def on_message(self, handler: Callable[[InboundMessage], Awaitable[None]]) -> None: ...
```

**Адаптеры:**
- `bot/telegram_adapter.py` → `TelegramTransport` (aiogram, **единственный на MVP**).
- `bot/whatsapp_adapter.py` → `WhatsAppTransport` (**прод, после первого контракта**).
- `bot/web_widget_adapter.py` → `WebWidgetTransport` (**прод, веб-виджет**).
- `bot/voice_adapter.py` → `VoiceTransport` (**дальний горизонт**).

**Критично:** `bot/` — это папка адаптеров транспорта, именно поэтому в [00-правила-проекта.md § П3](00-правила-проекта.md) запрещён импорт `aiogram` в `api/` и `core/`.

### Порт 3: `ContextStore` — состояние активного диалога

**Что ядро хочет:** «прочитай/запиши историю, профиль, шаг воронки по `session_id`».

```python
# core/context.py
class ContextStore(Protocol):
    async def get_history(self, session_id: str) -> list[Message]: ...
    async def append_message(self, session_id: str, msg: Message) -> None: ...
    async def get_profile(self, session_id: str) -> BuyerProfile: ...
    async def update_profile(self, session_id: str, patch: dict) -> None: ...
    async def get_funnel_step(self, session_id: str) -> str: ...
    async def set_funnel_step(self, session_id: str, step: str) -> None: ...
    async def delete_user(self, telegram_id: int) -> None: ...  # ФЗ-152 /stop
```

**Адаптеры:**
- `core/context_redis.py` → `RedisContextStore` (**по умолчанию**).
- `core/context_memory.py` → `InMemoryContextStore` (**только для тестов и локального dev**).

**Смена хранилища:** на проде, если Redis окажется мал — можно подложить `TarantoolContextStore` или `KeyDBContextStore` без правок в хэндлерах.

### Порт 4: `CRMClient` — передача лида в CRM магазина (**прод, после первого контракта**)

**Что ядро хочет:** «отдай лид в CRM, получи `external_crm_id`; будь идемпотентным».

```python
# core/crm.py
class CRMClient(Protocol):
    async def create_lead(
        self, lead: LeadPayload, idempotency_key: str,
    ) -> str: ...  # вернёт external_crm_id
    async def update_lead_status(
        self, external_crm_id: str, status: str,
    ) -> None: ...
```

**Адаптеры (на MVP не нужны):**
- `core/crm_bitrix24.py` → `Bitrix24Client`.
- `core/crm_amocrm.py` → `AmoCRMClient`.
- `core/crm_sheets.py` → `GoogleSheetsCRMClient` (простейший CRM для маленьких магазинов).

### Порт 5: `CatalogSource` — выгрузка каталога клиента-магазина (**прод, после первого контракта**)

**Что ядро хочет:** «отдай текущий срез SKU + цена + остаток».

```python
# core/catalog.py
class CatalogSource(Protocol):
    async def fetch_items(self) -> list[CatalogItem]: ...
```

**Адаптеры:**
- `core/catalog_1c.py` → `OneCCatalogSource`.
- `core/catalog_website.py` → `WebsiteParserCatalogSource` (парсер витрины).
- `core/catalog_csv.py` → `CSVCatalogSource` (ручная выгрузка).

### Порт 6: `Mailer` / `PaymentGateway` (**не на MVP и не в первой прод-версии**)

Включено в этот список для полноты и для одного и того же шаблона на будущее.

- **Mailer** — отправка писем (КП, уведомления). Адаптер: `UnisenderMailer`, `YandexMailMailer`, `SMTPMailer`.
- **PaymentGateway** — приём оплат (если появится SaaS-переупаковка). Адаптер: `YooKassaGateway`, `RobokassaGateway`, `TinkoffKassaGateway`.

На MVP не вводятся. Задел на будущее, чтобы при появлении не пришлось ломать `core/`.

## Что я сознательно **НЕ выбрал** и почему

Этот список важнее, чем «что выбрал». Он показывает осознанный отказ от соблазнов.

- **Микросервисы, event-sourcing, CQRS.** Это решения для больших команд и больших нагрузок; у меня один разработчик и один клиент. Монолит из двух сервисов (`api/` + `bot/`) с одним Redis — достаточен. Это уже обсуждено и отвергнуто в [02-сущности.md § «Вариант В»](02-сущности.md) и [03-база-данных.md § «Вариант В»](03-база-данных.md).
- **Kubernetes / Docker Swarm / Nomad.** Для 1 инстанса бота + 1 инстанса API — пушкой по воробьям; разворачивается через `systemd` на одном VPS. На проде, когда появится горизонтальное масштабирование — пересмотрим; пока — не трачу жетон.
- **Собственная LLM на Ollama / Llama / Mistral.** Для нормального качества нужны видеокарты от 24 ГБ, хостинг — от 50 000 ₽/мес, съедает всю экономику MVP; качество открытых моделей на русском — ниже GigaChat; разработчик уходит в devops, не в продукт.
- **OpenAI / Anthropic / Google Gemini в продакшене.** Запрещено по ФЗ-152 (ст. 12 — трансграничная передача). В dev-режиме на анонимных данных через OpenRouter — допустимо для сравнений; на проде — нет. Явно зафиксировано в [00-правила-проекта.md § П7б](00-правила-проекта.md).
- **MongoDB, Cassandra, DynamoDB.** Нам нужны FK (каскадное удаление ПДн), CHECK (валидация ролей, статусов), UNIQUE (идемпотентность `external_crm_id`) — всё это нативно только в реляционной БД; документные БД здесь только добавят ручной работы.
- **Elasticsearch / Meilisearch / Typesense.** Полнотекстового поиска по 12–14 моделям ТВ не требуется; на проде по каталогу магазина (несколько сотен SKU) PostgreSQL с `GIN+trigram` закроет вопрос без отдельного поискового движка.
- **Kafka / RabbitMQ / NATS.** Потоки сообщений одного магазина — килобайты в сутки; очередь на Redis (arq) закрывает их с запасом; тащить в стек брокер сообщений уровня «миллион событий в секунду» — не адекватно задаче.
- **Celery.** Sync-first, с asyncio-клиентами FastAPI/aiogram клеится через боль; выигрыша в скорости/надёжности над arq в нашем масштабе нет — только лишняя сложность.
- **Собственный почтовый сервер.** Разворачивать postfix + DKIM + SPF + reverse-DNS только чтобы отправить 10 писем КП — дороже, чем купить SendPulse / Unisender на 300 ₽/мес.
- **Собственная инфраструктура CI/CD** (GitLab Runner / Jenkins / Drone). На MVP деплой — `git pull && systemctl restart`; этого хватает. GitHub Actions включим, когда появится прод и несколько окружений; сейчас — не трачу жетон.
- **Grafana + Prometheus + Loki на MVP.** UptimeRobot (бесплатный пинг раз в 5 минут) + stdout-логи в journald — закрывают MVP-мониторинг. Grafana появится на проде, когда появится несколько метрик, которые имеет смысл сравнивать во времени.
- **Zabbix / Nagios.** То же — для одного VPS с одним ботом UptimeRobot покрывает 100% потребностей.
- **Webhook от Telegram на MVP.** Telegram читается через long-poll ([04-потоки-данных.md § 4.1](04-потоки-данных.md)) с NL-сервера — HTTPS-эндпоинт наружу на NL не поднимаем. Переключимся на webhook, когда появится несколько инстансов бота или возникнет узкое место по задержке. Nginx + Let's Encrypt всё равно нужны **на РФ-сервере** для HTTPS между NL и Core API — это не экзотика, а стандартная связка под whitelist IP.
- **gRPC / Protobuf между Core API и Bot.** HTTP+JSON через `httpx` даёт прекрасную задержку; текстовое представление — удобнее для отладки.
- **ORM поверх PostgreSQL с автогенерацией миграций в проде без ревью** (а-ля Prisma `db push`). На прод-версии миграции идут через Alembic с ручным ревью — так заложено в [03-база-данных.md § М1–М7](03-база-данных.md). SQLAlchemy 2.x планируется, но решение финализируется отдельной строкой в [decisions.md](decisions.md) при подключении PostgreSQL.
- **Admin-панель на MVP** (Django-admin, FastAPI-admin, SQLAdmin). Правка промпта и моделей — через git-коммит, не через UI; админка появится после первого контракта вместе с реальным каталогом.
- **A/B-тесты и фиче-флаги на MVP** (GrowthBook, Unleash). Пока у меня один клиент — тестировать не на ком; это строка в бэклоге «после первого контракта» ([mvp.md § 7](../idea/mvp.md)).
