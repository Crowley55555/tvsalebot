## Что здесь и чего нет

**Здесь.** Где физически лежит каждый файл будущего кода, какой у него интерфейс наружу, что он передаёт соседу и в каком виде, какой адаптер стоит перед каждым внешним сервисом, какая папка закреплена за каким окном Claude.

**Чего нет.** Это одно приложение в одном git-репозитории с одним деплоем на двух серверах из [05-стек.md § «Хостинг»](05-стек.md) (NL = `bot/`, РФ = всё остальное). Это **не** микросервисы, не монорепа из нескольких приложений, не event-sourcing — всё это сознательно отвергнуто в [02-сущности.md § «Вариант В»](02-сущности.md), [03-база-данных.md § «Вариант В»](03-база-данных.md), [05-стек.md § «Что я сознательно НЕ выбрал»](05-стек.md).

**Пустых папок под будущее нет.** Структура наращивается файлами, когда появляется задача. Папки для «после первого контракта» (каталог, лиды, CRM, веб-виджет, админка) здесь **не создаются** — они обозначены словами «появится при подключении …» и реально заводятся отдельным решением в [decisions.md](decisions.md).

## Выбор раскладки: три варианта и честное сравнение

Задача была — не записать первый пришедший в голову вариант. Сравнил три осмысленных подхода, под пять принципов из задания (вертикальные срезы + слои, один файл — одна задача, одна дверь на модуль, зависимости только вниз, адаптер на каждый внешний сервис).

### Вариант A — «две папки по частям продукта» (как в [mvp.md § 3](../idea/mvp.md))

```
api/     — весь Core API
bot/     — весь Telegram-бот
core/    — всё ядро, все порты, все адаптеры, вся бизнес-логика
```

**Плюсы:**
- Самый короткий путь, повторяет исходный набросок из mvp.md.
- Легко стартовать: три папки — три файла, не ошибёшься.

**Минусы:**
- `core/` становится свалкой: туда ложатся и доменные сущности (User, Session), и порты (LLMClient), и адаптеры (GigaChatClient), и бизнес-логика (воронка, рекомендация), и Redis-клиент. Правило «один файл — одна ответственность» ломается на уровне самой папки.
- Фичи (вести диалог, собрать согласие, удалить данные, выдать рекомендацию, переход в B2B) размазаны по `core/` — нельзя сказать «эта фича живёт в этой папке», значит нельзя закрепить фичу за одним окном Claude без конфликтов.
- Четвёртый принцип (домен не импортирует инфраструктуру) не виден в структуре — он есть только в комментариях.

### Вариант B — классический DDD в четыре слоя

```
domain/           — сущности + порты
application/      — usecases (ApplicationService)
infrastructure/   — адаптеры
interfaces/       — api + bot
```

**Плюсы:**
- Строго отражает четвёртый принцип: `domain/` ничего не импортирует, `application/` импортирует `domain/`, `infrastructure/` реализует порты, `interfaces/` — транспорт.
- Проверенный в индустрии подход.

**Минусы:**
- Для человека без техобразования слова «application / interfaces / usecases» — иностранные. Пользователь просил «самый понятный для человека без техобразования».
- Горизонтальная нарезка выигрывает в чистоте границ, но ломает первый принцип (вертикальные срезы): фича «собрать согласие» живёт одновременно в `application/consent_service.py` и `interfaces/bot/handlers/start.py` — одно окно Claude трогает оба файла, другое окно — ни одного.
- Для MVP на 3–4 недели и 5 фич — лишние тонкие прослойки.

### Вариант C — «фичи в своей папке + ядро + адаптеры» (выбран)

```
api/              — вход через HTTP (роуты, схемы, DI)
bot/              — вход через Telegram (хэндлеры, кнопки, клиент к api/)
features/         — бизнес-фичи, каждая в своей папке с одной дверью наружу
domain/           — сущности, типы, доменные ошибки, порты (интерфейсы)
infrastructure/   — адаптеры к внешним сервисам (gigachat, redis, glitchtip, …)
composition/      — сборка приложения, DI-контейнер, настройки окружения
prompts/          — тексты и промпт (правило П1)
scripts/          — служебные скрипты (smoke, test_scenarios)
tests/            — тесты, зеркалят структуру кода
landing/          — лендос-одностраничник
```

**Плюсы:**
- Названия папок на человеческом языке: «вход через HTTP», «вход через Telegram», «бизнес-фичи», «правила предметной области», «подключение к чужим сервисам», «сборка приложения», «тексты и промпт». Это читается без словаря.
- Каждая фича MVP (dialog, consent, deletion, recommendation, b2b) живёт в своей подпапке `features/<fname>/` с одним файлом-экспортом `__init__.py` — её целиком правит одно окно Claude, никто чужой внутрь не ходит.
- Домен (`domain/`) НЕ импортирует инфраструктуру — он объявляет порты, инфраструктура их реализует. Четвёртый принцип виден прямо в дереве.
- Каждый внешний сервис — отдельный файл-адаптер в `infrastructure/<kind>/<vendor>.py`. Пятый принцип (имя адаптера = имя вендора) соблюдается физически.
- Правила П2 и П3 из [00-правила-проекта.md](00-правила-проекта.md) проверяются простым `grep`: «есть ли `aiogram` в `api/` или `features/` — нет? хорошо», «есть ли `httpx.post` вне `infrastructure/` — нет? хорошо».

**Минусы:**
- На три папки больше, чем в варианте A. Для MVP с 10 файлами это заметный оверхед — компенсируется тем, что проект доживёт до прод-версии с десятками файлов, и правила границ окупят каждую лишнюю букву.
- `composition/` — слово иностранное; его человек без техобразования увидит один раз (при чтении этого файла) и может больше туда не ходить, всё поведение контейнера — одна функция в одном файле.

### Что выбрал и почему — одним предложением

**Выбрал вариант C.** Он единственный одновременно: даёт каждой фиче свою папку (вертикальный срез и одно окно = одна фича), сохраняет чёткий горизонтальный слой с портами в домене и адаптерами в инфраструктуре (имя вендора в имени файла — найти и заменить тривиально), и остаётся понятным без техбэкграунда — потому что каждая папка названа тем, что в ней лежит, а не тем, как это называется в академии.

### Что отверг — одним предложением

Монолит одним файлом (вариант A) — потому что `core/` разрастается в свалку, где фичи, порты и адаптеры живут вперемешку, а это ломает первый, второй и четвёртый принцип сразу. Микросервисы и монорепа из нескольких приложений — отвергнуты ещё в [02-сущности.md § «Вариант В»](02-сущности.md) и [05-стек.md § «Что я сознательно НЕ выбрал»](05-стек.md): один разработчик, один клиент, одна виртуалка на РФ-стороне — микросервисы здесь пушкой по воробьям.

**Проверка 1: ни одной пустой папки под будущее.** Папки `infrastructure/crm/`, `infrastructure/catalog/`, `infrastructure/db/` обозначены комментариями «появится при подключении …» и физически **не создаются** в MVP. То же про `migrations/` (Alembic) — появится вместе с первой PostgreSQL-миграцией после первого контракта.

**Проверка 2: ни одного микросервиса.** `api/` и `bot/` — это две точки входа одного приложения с одним `pyproject.toml`, одним Redis, одним git-репозиторием. На NL-сервер при деплое едет только `bot/ + composition/env.py + bot/settings.py + bot/core_api_client.py`, на РФ-сервер — всё остальное; это раздельный запуск, а не раздельный проект.

**Проверка 3: все сущности из [02-сущности.md](02-сущности.md) нашли свою часть.**

| Сущность | Где живёт в коде |
|---|---|
| Пользователь | `domain/entities.py: User` + `features/consent/` + `features/deletion/` |
| Диалог (Session) | `domain/entities.py: Session` + `features/dialog/` |
| Сообщение (Message) | `domain/entities.py: Message` — часть истории внутри сессии |
| Профиль покупателя | `domain/entities.py: BuyerProfile` + `features/dialog/profile_update.py` (встроен в диалог, не отдельный модуль — его природа из [02-сущности.md § 2](02-сущности.md)) |
| Рекомендация | `domain/entities.py: Recommendation` + `features/recommendation/` |
| Модель ТВ | `domain/entities.py: TVModel` + `infrastructure/tv_catalog/markdown_source.py` (справочник, читается из `prompts/models.md`) |
| Факт удаления данных | `features/deletion/deletion_log.py` + `prompts/policy.md` для политики |

Профиль и Рекомендация **не стали** отдельными top-level модулями — потому что по словарю это части Диалога. Профиль — внутренности `features/dialog/`, Рекомендация — отдельный `features/recommendation/`, потому что у неё отдельный шаг (`preparing_recommendation`) и отдельный промпт, но её жизненный цикл всё равно внутри сессии.

## 2. Таблица модулей

Для каждого модуля — что делает одной фразой, от кого зависит, что отдаёт наружу (**публичный интерфейс — только через `__init__.py`**), какими файлами владеет. Чужие ходят только через дверь; внутренности модуля правятся его хозяином, снаружи — нет.

### 2.1. Транспортный слой (вход)

| Модуль | Что делает | Зависит от | Отдаёт наружу (дверь) | Владеет |
|---|---|---|---|---|
| `api/` | Принимает HTTP-запросы `POST /chat`, `POST /reset`, `POST /gdpr/stop`, `GET /health`. Валидирует Pydantic. Передаёт в `features/`. | `composition/`, `features/`, `domain/` | ASGI-приложение `api.main.app` (запускается Uvicorn’ом). Больше ничего. | `main.py`, `routes.py`, `schemas.py`, `deps.py`, `middleware.py`, `settings.py` |
| `bot/` | Принимает Telegram-апдейты через long-poll. Проксирует в `POST /chat` на Core API. Отрисовывает ответы и клавиатуры. | HTTP к `api/` через `bot/core_api_client.py`, `composition/env.py` | Корутина `bot.main.run()` (запускается `python -m bot.main`). Внутренности недоступны. | `main.py`, `dispatcher.py`, `handlers/`, `keyboards.py`, `core_api_client.py`, `settings.py` |

### 2.2. Фичи (вертикальные срезы бизнес-логики)

Каждая фича — одна дверь, один `__init__.py`, остальные файлы — внутренности.

| Модуль | Что делает одной фразой | Зависит от | Дверь (из `__init__.py`) | Владеет |
|---|---|---|---|---|
| `features/dialog/` | Ведёт один шаг диалога: собирает контекст, обновляет профиль, зовёт LLM, пишет историю. | `domain/`, порты `LLMClient` + `ContextStore` + `TVCatalog` | `handle_user_message(cmd: HandleUserMessageCommand) -> DialogReply` | `service.py`, `funnel.py`, `profile_update.py`, `reply_builder.py` |
| `features/consent/` | Хранит и проверяет факт согласия на ПДн, версию политики. | `domain/`, порт `ContextStore` | `grant_consent(telegram_id, policy_version) -> None`, `has_consent(telegram_id) -> bool` | `service.py` |
| `features/deletion/` | Удаляет все данные пользователя по `/stop`, пишет анонимную запись в журнал удалений. | `domain/`, порты `ContextStore` + `AlertSink` | `delete_user_data(telegram_id, reason: Literal["user_stop","user_delete","retention"]) -> None` | `service.py`, `deletion_log.py` |
| `features/recommendation/` | Генерирует финальную рекомендацию (2–3 модели + обоснование + блок про безопасную приёмку). | `domain/`, порты `LLMClient` + `TVCatalog` + `ContextStore` | `build_recommendation(session_id) -> Recommendation` | `service.py`, `selector.py`, `safety_block.py` |
| `features/b2b/` | Отдаёт пользователю короткое B2B-КП (вручную по `/для_магазина` или в конце диалога после рекомендации). | `domain/`, порт `ContextStore` (пометить `b2b_cta_shown=true`) | `send_b2b_pitch(session_id, entry_point) -> B2BReply` | `service.py` |

**Жёсткое правило по дверям:** снаружи фичи импортируется **только** то, что экспортируется из её `__init__.py`. Прямой импорт `from features.dialog.service import ...` или `from features.dialog.funnel import ...` **запрещён**. Это проверяется в CI (линт на import-boundaries) и в код-ревью.

### 2.3. Домен (правила без зависимостей)

| Модуль | Что делает | Зависит от | Дверь | Владеет |
|---|---|---|---|---|
| `domain/` | Описывает «из каких кусков устроен продукт»: сущности, типы, доменные ошибки. **Не импортирует ничего, кроме стандартной библиотеки и Pydantic.** | — | Прямой импорт `from domain import User, Session, …, LLMClient, ContextStore, …` | `entities.py`, `value_objects.py`, `errors.py`, `ports/*.py` |
| `domain/ports/` | Описывает «что ядро хочет от внешнего мира»: пять `Protocol`-интерфейсов. Это **контракт**, который нельзя менять без строки в [decisions.md](decisions.md). | — | Прямой импорт `from domain.ports import LLMClient, ContextStore, TVCatalog, ErrorReporter, AlertSink` | `llm.py`, `context_store.py`, `tv_catalog.py`, `error_reporter.py`, `alert_sink.py` |

### 2.4. Инфраструктура (адаптеры)

Один файл-адаптер = один вендор. Имя файла — **имя вендора**. Это пятый принцип в чистом виде.

| Модуль | Реализует порт | Что делает | Зависит от | Дверь |
|---|---|---|---|---|
| `infrastructure/llm/gigachat.py` | `LLMClient` | HTTP-клиент GigaChat 2 Pro: OAuth2, chat, таймаут, parsing | `domain.ports.llm`, `httpx`, `settings` | класс `GigaChatClient` |

| `infrastructure/context/redis_store.py` | `ContextStore` | Redis-реализация: истории, профиль, шаг воронки, локи | `redis.asyncio`, `settings` | класс `RedisContextStore` |
| `infrastructure/context/memory_store.py` | `ContextStore` | In-memory реализация для тестов | — | класс `InMemoryContextStore` |
| `infrastructure/context/keys.py` | — | Формат всех Redis-ключей в одном месте | — | функции `dialog_history_key(sid)`, `lock_key(sid)`, … |

| `infrastructure/tv_catalog/markdown_source.py` | `TVCatalog` | Парсит `prompts/models.md` → `list[TVModel]`, кэширует | `domain.entities.TVModel`, `pathlib` | класс `MarkdownTVCatalog` |

### 2.5. Композиция (DI, настройки)

| Модуль | Что делает | Зависит от | Дверь | Владеет |
|---|---|---|---|---|
| `composition/env.py` | **Единственное место**, где читаются переменные окружения в приложении. Pydantic-settings с валидацией. | `pydantic_settings` | `AppSettings`, функция `get_settings()` | `env.py` |

## 3. Контракты на границах — что одна часть передаёт другой и в каком виде

Это главный раздел. Если контракты не зафиксировать — части пишутся по отдельности и потом не стыкуются. Каждый контракт меняется **осознанно, с записью в [decisions.md](decisions.md)** (правило П5); изменивший обязан обновить **обе** стороны границы.

### 3.1. Граница `bot/` → `api/` (внешний HTTP между NL-сервером и РФ-сервером)

**Как разговаривают:** HTTP+JSON через `httpx` поверх TLS. Заголовок `Authorization: Bearer <CORE_API_BEARER_TOKEN>`.

**Эндпоинт `POST /chat`:**

Вход:
```json
{
  "telegram_id": 123456789,
  "session_id": "9b1c2d3e-...-uuid-v4",
  "message": "Хочу PS5-ТВ",
  "message_kind": "text",
  "update_id": 987654321,
  "entry_point": "start"
}
```

Выход (успех):
```json
{
  "reply": "Отлично, PS5 важна. В светлой или тёмной комнате смотрим?",
  "funnel_step": "ask_light",
  "buttons": [
    {"id": "light_bright", "label": "Светлая"},
    {"id": "light_dark", "label": "Тёмная"},
    {"id": "light_mixed", "label": "Смешанная"}
  ],
  "recommendation": null
}
```

Выход (ошибка — валидная проблема, не стек-трейс):
```json
{
  "error": "consent_required",
  "user_message": "Сначала подтверди обработку персональных данных кнопкой под сообщением /start."
}
```

Коды ответа: `200` (OK), `400` (битый JSON), `401` (bearer-токен не прошёл), `409` (уже обрабатываем это сообщение — лок, см. 04-потоки § 4.3), `429` (упёрлись в дневной потолок токенов), `503` (LLM недоступен после ретраев).

**Эндпоинт `POST /reset`:** вход `{"telegram_id":123,"session_id":"<old-uuid>"}` → выход `{"new_session_id":"<new-uuid>","reply":"<текст нового приветствия воронки>"}`.

**Эндпоинт `POST /gdpr/stop`:** вход `{"telegram_id":123,"reason":"user_stop"}` → выход `{"deleted": true}` или `{"deleted": true, "note": "nothing_to_delete"}`.

**Эндпоинт `GET /health`:** выход `{"status":"ok","redis":"ok","llm_last_check":"2026-10-25T19:50:00Z"}`.

**Pydantic-схемы живут в `api/schemas.py`** и **импортируются из `bot/core_api_client.py`** через клиентскую копию (на NL-стороне). Чтобы не было дрейфа, при изменении схемы — **одновременно** правятся `api/schemas.py` и `bot/core_api_client.py` в одном коммите, и в [decisions.md](decisions.md) появляется строка.

### 3.2. Граница `api/` → `features/dialog/` (внутренний вызов)

**Как разговаривают:** Python-функция через контейнер зависимостей.

Контракт:
```python
# domain/commands.py (новый файл внутри domain/)
class HandleUserMessageCommand(BaseModel):
    telegram_id: int
    session_id: str
    message_text: str
    message_kind: Literal["text", "button"]
    entry_point: Literal["start", "for_shop", "test"]

class DialogReply(BaseModel):
    reply_text: str
    funnel_step: str                      # value_objects.FunnelStep as str
    buttons: list[ButtonSpec]
    recommendation: Recommendation | None # заполнено, если финал
```

Вход: `HandleUserMessageCommand`. Выход: `DialogReply`. Ошибки — поднимаются типизированные доменные исключения из `domain/errors.py` (`ConsentRequired`, `LLMUnavailable`, `BudgetExceeded`), ловит их `api/routes.py` и мапит в HTTP-коды.

### 3.3. Граница `features/*` → `domain/ports/*` (ядро → внешний мир)

Пять портов, по одному файлу на каждый. Это **стабильный контракт**, меняется только осознанно (строка в [decisions.md](decisions.md) + обновление **всех** адаптеров + обновление всех фич, которые его зовут).

**Порт `LLMClient` (`domain/ports/llm.py`):**
```python
class ChatResult(BaseModel):
    text: str
    tokens_used: int
    provider: str
    duration_ms: int

class LLMClient(Protocol):
    async def chat(
        self,
        system_prompt: str,
        history: list[Message],
        *,
        max_tokens: int = 1024,
        timeout_s: float = 10.0,
    ) -> ChatResult: ...
```

Ошибки: адаптер **ловит** HTTP-ошибки (5xx/timeout/429) и **ретраит** внутри себя 3 раза с задержкой 0.5 → 2 → 5 с ([04-потоки § 3.3](04-потоки-данных.md)); если после всех попыток не вышло — поднимает `LLMUnavailable` из `domain/errors.py`. Фича `features/dialog/` этого не знает и видит либо `ChatResult`, либо исключение.

**Порт `ContextStore` (`domain/ports/context_store.py`):**
```python
class ContextStore(Protocol):
    async def get_history(self, session_id: str, limit: int = 20) -> list[Message]: ...
    async def append_message(self, session_id: str, msg: Message) -> None: ...
    async def get_profile(self, session_id: str) -> BuyerProfile: ...
    async def update_profile(self, session_id: str, patch: dict) -> None: ...
    async def get_funnel_step(self, session_id: str) -> FunnelStep: ...
    async def set_funnel_step(self, session_id: str, step: FunnelStep) -> None: ...
    async def resolve_or_create_session(self, telegram_id: int, session_id: str, entry_point: EntryPoint) -> Session: ...
    async def delete_user(self, telegram_id: int) -> int: ...  # возвращает число удалённых ключей
    async def acquire_lock(self, session_id: str, ttl_s: int = 30) -> bool: ...
    async def release_lock(self, session_id: str) -> None: ...
```

Это единственный способ попасть в Redis (правило П4). `features/*` **никогда** не импортирует `redis` напрямую — только через `ContextStore`.

**Порт `TVCatalog` (`domain/ports/tv_catalog.py`):**
```python
class TVCatalog(Protocol):
    async def all(self) -> list[TVModel]: ...
    async def by_code(self, code: str) -> TVModel | None: ...
```

На MVP под ним — `MarkdownTVCatalog`, читающий `prompts/models.md`. На проде — `PostgresTVCatalog`, подключается без правок в `features/recommendation/`.

**Порт `ErrorReporter` (`domain/ports/error_reporter.py`):**
```python
class ErrorReporter(Protocol):
    def capture_exception(self, exc: BaseException, context: dict | None = None) -> None: ...
    def capture_message(self, msg: str, level: str = "info") -> None: ...
```

Используется глобально через `composition/container.py.error_reporter` в `api/middleware.py` и `bot/main.py`.

**Порт `AlertSink` (`domain/ports/alert_sink.py`):**
```python
class AlertSink(Protocol):
    async def send_dev_alert(self, text: str, level: Literal["info","warn","error"] = "warn") -> None: ...
```

Используется в `infrastructure/llm/budget.py` (при превышении потолка), в `features/deletion/` (на случай сбоя удаления — вторая линия обороны), в `scripts/sweep_abandoned.py` (прод).

### 3.4. Граница `features/dialog/` → `features/recommendation/`

**Как разговаривают:** прямой вызов через Python-функцию, оба модуля в одной process-памяти. Контракт — через `domain/commands.py`.

```python
# В features/dialog/service.py когда funnel_step == 'preparing_recommendation':
recommendation = await container.recommendation.build_recommendation(session_id)
```

Вход: `session_id: str`. Выход: `Recommendation` (объект из `domain/entities.py`). Ошибки: `LLMUnavailable`, `TVCatalogEmpty` — поднимаются типизированно.

### 3.5. Граница `prompts/` → код

Чтение файлов `.md` через `pathlib.Path(prompts_dir) / "system.md"`. Путь к папке `prompts/` берётся из `AppSettings.PROMPTS_DIR` (по умолчанию — `./prompts`). Все `.md`-файлы читаются **один раз при старте приложения** и кэшируются в контейнере; на проде правка `.md` требует `systemctl reload tvsalebot-api` (или сигнала SIGHUP с ре-чтением).

**Содержимое .md не парсится регулярками в коде.** Это текст, он идёт в LLM как есть (system_prompt), либо (для `prompts/models.md`) — через лёгкий YAML-блок во фронтматере, где лежат структурированные спеки.

Пример `prompts/models.md`:
```markdown
---
models:
  - code: QN90F
    trade_name: "Neo QLED QN90F"
    tv_class: neo_qled
    diagonals_inches: [55, 65, 75, 85]
    refresh_hz: 120
    brightness_nits: {min: 1500, max: 2000}
    hdmi: {version: "2.1", ports: 4}
    backlight: mini_led
    price_kopecks: {min: 12000000, max: 25000000}
    fits_short: "Светлая гостиная, кино, PS5"
    honest_caveats: "Нет Dolby Vision"
---

# Neo QLED QN90F

Полное описание под LLM: ...
```

Это даёт одновременно: читаемый человеком текст для LLM (сам markdown) + структурированные спеки для `MarkdownTVCatalog` (frontmatter). **Правило:** редактор может править и то, и другое, не прося разработчика.

## 4. Карта адаптеров к внешним сервисам

Полная таблица «кто куда ходит», чтобы по имени вендора найти файл и подменить за один коммит. Имя адаптера = имя вендора. Правило из `00-правила-проекта.md § П2`.

## 5. Карта владения: N параллельных окон Claude

Задача: разложить проект на непересекающиеся наборы папок, чтобы несколько окон Claude строили параллельно и не правили одни и те же файлы.

**Выбранное N = 5** (одно для контракта + четыре для строительства параллельно). Пять — потому что это ровно то число, при котором каждое окно получает связную область (транспорт, фичи, инфра, контент) и ни одно не остаётся с одним файлом. Можно сократить до N = 3, если на старте есть ровно один-два помощника; тогда окна Y1/Y2/Y3 ниже сворачиваются в одно «ядро + инфра + контент», а окно W1 остаётся как есть.

### 5.1. Окно W0 — Общий контракт (**строится первым, в одиночку, другие ждут**)

**Чем владеет:**
- `domain/__init__.py`, `domain/entities.py`, `domain/value_objects.py`, `domain/errors.py`
- `domain/ports/__init__.py`, `domain/ports/llm.py`, `domain/ports/context_store.py`, `domain/ports/tv_catalog.py`, `domain/ports/error_reporter.py`, `domain/ports/alert_sink.py`
- `domain/commands.py` (контракты фич: `HandleUserMessageCommand`, `DialogReply` и прочие cross-feature DTO)
- `api/schemas.py` (Pydantic HTTP-DTO границы `api/` ↔ `bot/`)
- `composition/env.py` (`AppSettings` — все переменные окружения, одно место)
- `prompts/` **структура** (список файлов и их формат, не содержимое — его параллельно пишет W4)

**Что зовёт через интерфейс:** ничего не зовёт — он только **объявляет** интерфейсы.

**Чего никогда не трогает:** `infrastructure/`, `features/*/`, `api/routes.py`, `bot/handlers/`, тела `prompts/*.md`, `scripts/`.

**Когда закрывается:** когда все остальные владельцы (W1–W4) **явно** согласовали контракт — читается `domain/ports/` и `api/schemas.py`, нет возражений, стоит зелёная строка в [decisions.md](decisions.md): «2026-ММ-ДД — зафиксирован общий контракт v1 (пять портов + три HTTP-схемы) для параллельной сборки». После этого **изменение любого файла из W0 — только с записью в [decisions.md](decisions.md) + уведомление всех остальных окон**.

### 5.2. Окно W1 — Транспортный слой (`api/` + `bot/`)

**Чем владеет:**
- Вся папка `api/`, **кроме** `api/schemas.py` (его владеет W0) → `main.py`, `routes.py`, `deps.py`, `middleware.py`, `settings.py`
- Вся папка `bot/` → `main.py`, `dispatcher.py`, `handlers/*.py`, `keyboards.py`, `core_api_client.py`, `settings.py`
- `composition/container.py` (сборка контейнера — потому что `api/deps.py` и `bot/main.py` его зовут)

**Что зовёт через интерфейс:**
- `features/*` через `composition.container` (двери фич из их `__init__.py`).
- Pydantic-схемы из `api/schemas.py` (прямой импорт — но меняет их только W0).

**Чего никогда не трогает:**
- Внутренности `features/*/` (прямой `from features.dialog.service import ...` запрещён).
- `infrastructure/*` (прямой импорт конкретного адаптера запрещён — всё через контейнер).
- `prompts/*.md` (их читают только `infrastructure/tv_catalog/` и `features/*/`).

### 5.3. Окно W2 — Фичи (`features/`)

**Чем владеет:**
- Вся папка `features/` — пять подпапок (`dialog/`, `consent/`, `deletion/`, `recommendation/`, `b2b/`).
- `tests/unit/features/*` и `tests/integration/test_full_dialog.py`.

**Что зовёт через интерфейс:**
- Порты из `domain/ports/` (прямой импорт `from domain.ports import LLMClient, ContextStore, TVCatalog`).
- Сущности из `domain/entities.py`.
- Соседние фичи — **только через их `__init__.py`** (например, `features/dialog/service.py` вызывает `features.recommendation.build_recommendation`).

**Чего никогда не трогает:**
- `infrastructure/*/*` (ни одного прямого импорта `GigaChatClient`, `RedisContextStore`).
- `api/`, `bot/`.
- `composition/container.py` (его правит W1; фичи получают зависимости как параметры конструктора).

### 5.4. Окно W3 — Инфраструктура (`infrastructure/`)

**Чем владеет:**
- Вся папка `infrastructure/` — `llm/`, `context/`, `alerting/`, `tv_catalog/`.
- `tests/unit/infrastructure/*`.
- Содержимое `.env.example` (имена переменных для адаптеров).

**Что зовёт через интерфейс:**
- Порты из `domain/ports/` (реализует их).
- Сущности из `domain/entities.py` (использует их как типы для возврата).

**Чего никогда не трогает:**
- `api/`, `bot/`, `features/`, `composition/container.py` (его правит W1).
- `prompts/*.md` (кроме чтения через `MarkdownTVCatalog` — но содержимое пишет W4).

### 5.5. Окно W4 — Контент и операционка (`prompts/` + `scripts/` + `landing/`)

**Чем владеет:**
- Все содержимое `prompts/*.md` (системный промпт, 12–14 моделей, 5 сценариев, формулировки воронки, политика).
- `scripts/*.py` (smoke-тесты, прогон сценариев).
- Вся папка `landing/`.
- `README.md`, `Makefile`.

**Что зовёт через интерфейс:**
- Содержимое `prompts/` читают `infrastructure/tv_catalog/markdown_source.py` и `features/dialog/`. W4 **соблюдает формат frontmatter** `prompts/models.md`, установленный W0 (структура YAML-блока — часть контракта).

**Чего никогда не трогает:**
- `.py`-файлов (кроме `scripts/*.py`, которые его собственные).
- `api/`, `bot/`, `features/`, `infrastructure/`, `domain/`.

### 5.6. Таблица «что имею — что зову — чего не трогаю»

| Окно | Чем владеет | Что зовёт через интерфейс | Чего никогда не трогает |
|---|---|---|---|
| **W0 — контракт** | `domain/`, `api/schemas.py`, `composition/env.py`, формат `prompts/` | ничего, только объявляет | тела `prompts/*.md`, `features/*/`, `infrastructure/*/`, `api/routes.py`, `bot/` |
| **W1 — транспорт** | `api/` (кроме schemas), `bot/`, `composition/container.py` | фичи через `features/*/__init__.py`, pydantic-схемы W0 | внутренности `features/*/`, `infrastructure/*/*`, `prompts/*.md` |
| **W2 — фичи** | `features/`, `tests/unit/features/` | порты W0, сущности W0, соседние фичи **через дверь** | `infrastructure/`, `api/`, `bot/`, `composition/container.py` |
| **W3 — инфра** | `infrastructure/`, `tests/unit/infrastructure/`, `.env.example` | порты W0 (реализует их) | `features/`, `api/`, `bot/`, `composition/container.py`, тела `prompts/` |
| **W4 — контент** | `prompts/*.md`, `scripts/`, `landing/`, `README.md`, `Makefile` | формат frontmatter W0 | любые `.py` вне `scripts/` |

**Жёсткое правило при параллельной работе:**
1. **W0 закрывается первым.** Никто кроме W0 не стартует, пока в [decisions.md](decisions.md) не появилась строка «общий контракт v1 зафиксирован».
2. **Изменение любого файла из W0 — только с записью в [decisions.md](decisions.md)** + уведомление всех остальных владельцев в текущем чате.
3. **Если W2 (фича) обнаружил, что ему не хватает поля в DTO/порте** — он **не правит** `domain/ports/*.py` сам. Пишет в чат «нужно расширить `LLMClient.chat` параметром `temperature`» → W0 обновляет порт → W3 обновляет все адаптеры → W2 продолжает.
4. **Любое окно** может **читать** любые файлы проекта (это проектный документ, не секрет). **Писать** — только в свою область.

### 5.7. Пересечения, которые пришлось назначить осознанно

- **`composition/container.py`** — отдан W1 (транспорт), а не W0 (контракт), потому что это **сборка**, а не декларация; её трогают при добавлении нового адаптера или фичи, что делают W2/W3, и им проще один раз добавить строку в контейнер в тот же PR, чем ждать W0.
- **`.env.example`** — отдан W3 (инфра), потому что переменные окружения на 90% про адаптеры (ключи GigaChat, URL Redis); доменные настройки (TTL сессии, лимит дневного бюджета) добавляет W3 по согласованию с W0.
- **`tests/integration/`** — делится: `test_api_chat.py` и `test_bot_handlers.py` — W1, `test_full_dialog.py` (5 сценариев end-to-end) — W2.
- **`infrastructure/alerting/telegram_alert.py`** — W3 (там единственное место вне `bot/`, где импортируется `aiogram`); это **должно быть зафиксировано в [decisions.md](decisions.md)** как осознанное исключение из правила П3.

## 6. Как добавить новый модуль (гайд владельцам окон)

> _Этот проект сейчас **не планируется к публикации в open-source** (из [00-правила-проекта.md § «Что сломать нельзя»](00-правила-проекта.md) и глобальных правил пользователя — ядро закрытое, промпт и бизнес-данные приватные). Поэтому раздел короткий: это рабочая памятка для окон, не публичный contrib-гайд._

### Новая бизнес-фича (например, «передача лида в CRM»)

1. Создать папку `features/<fname>/` с `__init__.py` + `service.py`.
2. В `__init__.py` экспортировать **одну функцию-дверь**: `send_lead_to_crm(session_id) -> LeadResult`.
3. Если нужен новый внешний сервис — добавить порт в `domain/ports/<name>.py` (это правит W0 с записью в [decisions.md](decisions.md)) и адаптер в `infrastructure/<kind>/<vendor>.py` (W3).
4. Зарегистрировать фичу в `composition/container.py` (W1).
5. Проброс через `api/routes.py` (новый эндпоинт `POST /lead`) — W1.
6. Тесты в `tests/unit/features/test_<fname>_service.py` — W2.
7. Строка в [decisions.md](decisions.md) формата `ГГГГ-ММ-ДД — добавлена фича <fname> — зачем`.

**Чужие файлы не правятся.** Если «нельзя не править» (например, появился новый шаг воронки) — это сигнал пересмотреть контракт, не хакать насквозь.

### Новый адаптер к существующему порту (например, второй CRM-вендор)

1. Создать `infrastructure/<kind>/<new_vendor>.py` (имя файла = имя вендора).
2. Реализовать все методы порта из `domain/ports/<name>.py`.
3. Добавить ветку в `infrastructure/<kind>/__init__.py` фабрике.
4. Добавить переменную в `composition/env.py` (расширить допустимые значения `CRM_PROVIDER`).
5. Строка в [decisions.md](decisions.md).

### Граница публикуемого (на будущее, если проект уйдёт в SaaS)

- **Публикуемо** (может уйти в open-source, если когда-нибудь появится «коробочная» версия из [vision.md § «Б»](../idea/vision.md)): `domain/`, `features/dialog/funnel.py` (без промптов), шаблоны портов `domain/ports/*.py`, абстрактные тесты `tests/unit/domain/`.
- **Приватно (никогда не публикуется):** `prompts/*.md` (это и есть главный актив, см. [principles.md § 8.1](../idea/principles.md)), `.env.example` в части имён-подсказок для секретов конкретного клиента, `scripts/requeue.py` (операционный), `landing/` (с цифрами и УТП), `.business/` (вне репо, см. [00-правила-проекта.md § П7г](00-правила-проекта.md)).
- **Красная линия:** если дойдёт до публикации — `prompts/` **не выходят** в публичный пакет; они остаются в приватной конфигурации арендатора.
