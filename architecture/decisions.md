# Журнал решений

> Единая лента архитектурных решений проекта **tvsalebot** (правило П5 из [00-правила-проекта.md](00-правила-проекта.md)).
> Формат строки: `ГГГГ-ММ-ДД — что меняем — почему (ссылка на материал)`.
> Записываем сюда: смену/добавление LLM-провайдера, изменение формата ключей Redis, изменение схем `POST /chat`, добавление нового канала, крупную правку `prompts/system.md`, подключение новой платной внешней услуги, миграции схемы БД.

## Лента

- 2026-10-26 — реализован тонкий сквозной срез F5 Walking Skeleton (plans/2026-06-08-vertical-slice.md): HTTP `POST /chat` + aiogram-бот + `RedisContextStore` отвечают эхом-счётчиком «видел, это твоя N-я реплика» без LLM и воронки. v0-усечения контракта (строкой здесь, чтобы не плодить отдельные записи): (а) `ChatRequest { telegram_id, text, update_id? }` без `session_id/buttons/funnel_step/recommendation` — расширим в F6; (б) порт `ContextStore` на этом шаге имеет только `append_message`, `get_history_length`, `mark_update_seen` — полный порт из [08-структура-кода.md § 3.3](08-структура-кода.md) наращиваем по мере фич; (в) `session_key = str(telegram_id)` — сессия = пользователь до появления воронки; (г) дедуп повторных Telegram `update_id` через SETNX `idempotency:update:<id>` c TTL 60 с (защита от long-poll retry без полноценного лока на сессию из [04-потоки § 4.3](04-потоки-данных.md)); (д) `GET /health` не вводим до вечера с деплоем. Приёмочный тест на `InMemoryContextStore` зелёный, Redis-адаптер проверяется вручную через `redis-cli LLEN`. Правила П1/П2/П3/П4 проверены грепом — чисто.
- 2026-10-25 — зафиксирована нормализованная реляционная схема прод-БД (10 таблиц + 2 прод-расширения, PostgreSQL, переносимый SQL): физическое удаление для ПДн, мягкое — для справочников и каталога, append-only для аудит-лога — закрывает ФЗ-152-удалятор одним `DELETE users` с каскадом и даёт один стиль схемы для диалогов и каталога/лидов, вместо JSONB-гибрида или event-sourcing — [03-база-данных.md](03-база-данных.md).
- 2026-10-25 — закрыты три открытых вопроса из [02-сущности.md § «Чего ещё не знаю»](02-сущности.md): несколько диалогов на пользователя (под аналитику конверсии); отдельного «типа пользователя» нет — хватает `users.entry_point` (`start`/`for_shop`/`test`); сообщения на прод выносим в отдельную таблицу `messages` (под отчёты и аналитику) — [03-база-данных.md](03-база-данных.md).
- 2026-10-25 — удалён черновик `architecture/schema.prisma`: стек прод-БД пока не выбран ([05-стек.md](05-стек.md) — черновик), конкретный формат схемы (SQLAlchemy / Prisma / sqlc) генерируется из переносимого SQL в [03-база-данных.md](03-база-данных.md) после финализации стека.
- 2026-10-25 — зафиксированы потоки данных (20 событий, лёгкая/тяжёлая работа, очередь задач с ретраями и карантином, идемпотентность LLM/CRM, машина состояний воронки с таймаутом и дневным потолком расходов): MVP — long-poll Telegram + синхронный LLM-вызов в хэндлере + Redis-лок от двойных кликов; прод — arq-очередь поверх того же Redis + ключ идемпотентности LLM + external_crm_id UNIQUE против двойной передачи лида — [04-потоки-данных.md](04-потоки-данных.md).
- 2026-10-25 — финализирован стек: Python 3.11 + FastAPI + Pydantic v2 + aiogram 3.x + Redis 7 на MVP → + PostgreSQL 15 Managed в РФ-облаке + arq на проде; LLM — GigaChat 2 Pro Freemium → pay-as-you-go через порт `LLMClient` с YandexGPT-fallback; жетон №1 потрачен на LLM, №2 зарезервирован под arq (прод), №3 свободен — закрывает ФЗ-152 (база и LLM в РФ) + 0 ₽/мес на MVP (Freemium 40 млн токенов/год) при максимально скучном проверенном стеке — [05-стек.md](05-стек.md).
- 2026-10-25 — хостинг: используются уже выделенные серверы по схеме «NL = stateless-транспорт aiogram, РФ = Core API + Redis + БД»; связь HTTPS + bearer-токен + IP-whitelist в nftables; nginx + Let's Encrypt только на РФ-сервере; NL-сервер не хранит ПДн на диске/в кэше дольше одного запроса, логи обезличены (хэш `telegram_id`); перед выдачей ссылки реальным покупателям — уведомление РКН о трансграничной передаче ПДн — [05-стек.md § «Хостинг»](05-стек.md).
- 2026-10-25 — безопасность финализирована по четырём темам: (1) ПДн — физическое удаление по `/stop` с каскадом FK, анонимизация перед LLM, оператор — заказчик, вся база — в РФ; (2) опасная тройка — на MVP не собирается (у LLM нет внешних действий, только текстовый ответ), на проде вводим reader-агент без инструментов + writer-агент с единственным инструментом `create_lead` и без доступа к сырому тексту; (3) ИИ-расходы — потолок 100 000 токенов/день на MVP и 1000 ₽/день на проде с авто-стопом в `core/budget.py`, три алерта (10 падений подряд, очередь > 50, 80% бюджета), Lite-модель на reader, Pro-модель на рекомендацию, prompt caching системного блока; (4) роли — посетитель/клиент/клиент-магазин/разработчик/автоматика, принцип ползунка «сам — спросить — явное подтверждение», доступ разработчика к Redis/БД через SSH на MVP — сознательный компромисс до перехода в SaaS — [07-безопасность.md](07-безопасность.md).
- 2026-10-25 — зафиксирована структура кода (вариант C — вертикальные срезы `features/*` + домен и пять портов в `domain/` + адаптеры с именем вендора в `infrastructure/<kind>/<vendor>.py` + сборка в `composition/`): каждая фича MVP (dialog/consent/deletion/recommendation/b2b) живёт в своей папке с одной дверью наружу через `__init__.py`, зависимости строго вниз, греп по П1/П2/П3 проходит; осознанное исключение П3 — единственный импорт `aiogram.Bot` вне `bot/` в `infrastructure/alerting/telegram_alert.py` для dev-алертов разработчику; владение разложено на 5 окон (W0 — общий контракт первым, W1 — транспорт, W2 — фичи, W3 — инфра, W4 — контент); отвергнуты «монолит одним `core/`» (ломает П1/П2/П4) и классический DDD в слоях (проигрывает вертикальным срезам при одном разработчике и 5 фичах MVP) — [08-структура-кода.md](08-структура-кода.md).
