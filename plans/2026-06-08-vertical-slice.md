# Вертикальный срез: тончайший живой канал

Дата: 2026-06-08
Статус: черновик
Правило: ничего не реализовано, план только для согласования.

## 1. Срез вечера одной строкой

**Когда пользователь пишет любое текстовое сообщение боту в Telegram, продукт сохраняет его в истории диалога в Redis и отвечает в чат «видел, это твоя N-я реплика» — где N приходит из Redis.**

Это тонкий канал F5 Walking Skeleton **без LLM и без воронки**: сквозной путь через все слои (Telegram → aiogram-handler → HTTP → Core API → Redis → ответ по тому же пути обратно) с ровно одним захардкоженным ответом, не требующим GigaChat. Так закрываются интеграционные риски транспорта (long-poll Telegram, межпроцессный HTTP, Redis), пока LLM, промпты и воронка не трогаются.

## 2. Что входит сегодня

- Один aiogram-handler на любой текст в приватном чате (без inline-кнопок, без команд, кроме неявного `/start` как обычного текста).
- Один FastAPI-эндпоинт `POST /chat` с двумя Pydantic-схемами (`ChatRequest { telegram_id, text }`, `ChatResponse { reply }`) в `api/schemas.py` — скелет будущего контракта из F0.
- Один адаптер Redis: `append_message(telegram_id, role, text)` и `get_history_length(telegram_id)` поверх списка `dialog:<telegram_id>:history` ([03-база-данных.md](../architecture/03-база-данных.md)).
- Минимальный `composition/container.py`, который собирает `RedisContextStore` → `features/dialog/handle_user_message` (пока без вызова LLM) и отдаёт в `api/routes.py`.
- `.env.example` с `BOT_TOKEN`, `REDIS_URL`, `CORE_API_URL` — без секретов, только имена переменных.
- Локальный запуск в трёх окнах: `docker run redis`, `uvicorn api.main:app`, `python -m bot`.

## 3. Сценарии приёмки

### Главный путь (успех)

**Когда** в терминале 1 поднят `docker run -p 6379:6379 redis:7-alpine`, в терминале 2 — `uvicorn api.main:app --port 8000`, в терминале 3 — `python -m bot` с валидным `BOT_TOKEN` dev-бота, **и** пользователь открывает этого бота в Telegram и пишет три сообщения подряд: «привет», «тест», «ещё раз», **то** на каждое сообщение бот отвечает в чат соответственно: «видел, это твоя 1-я реплика», «видел, это твоя 2-я реплика», «видел, это твоя 3-я реплика». Техническая проверка: `redis-cli LLEN dialog:<telegram_id>:history` возвращает `3`, `redis-cli LRANGE dialog:<telegram_id>:history 0 -1` показывает три строки в правильном порядке.

### Путь ошибки

**Когда** Redis остановлен (`docker stop <id>` или `redis-cli shutdown nosave`) и пользователь пишет боту «привет», **при условии что** `httpx` в боте настроен на таймаут 5 с, а FastAPI ловит `redis.exceptions.ConnectionError` и отдаёт `503 { "detail": "storage_unavailable" }`, **то** бот отвечает в чат одной вежливой репликой «секунду не могу ответить, попробуй написать ещё раз через минуту» (**не** стек-трейсом, **не** «Error: 503», **не** молчанием). В stdout бота — ровно одна строка уровня ERROR с `request_id` и причиной `storage_unavailable`. После `docker start <id>` следующее сообщение пользователя обрабатывается нормально, счётчик продолжается с того места, где оборвался (список в Redis поднимается с нуля — ожидаемо, так как это in-memory без AOF; пункт в журнале решений не нужен, персистентность Redis — тема F22).
